## 1. Concepto de construcción de sistemas de información

La construcción de sistemas de información es el conjunto de actividades de diseño, desarrollo, integración, pruebas, implantación y mantenimiento necesarias para crear un sistema que resuelva una necesidad concreta de la organización.

En este proceso no basta con generar código: es necesario asegurar que el sistema cumple los requisitos funcionales, las restricciones técnicas, las necesidades de seguridad y la calidad esperada por los usuarios y la organización.

La construcción de software se apoya en tres pilares clave:

- la definición correcta de requisitos;
- la aplicación de métodos y técnicas adecuadas;
- la validación continua del sistema mediante pruebas y revisión.

## 2. Pruebas de software: tipologías y enfoques

Las pruebas de software son actividades sistemáticas orientadas a detectar defectos y verificar que el sistema cumple los requisitos planteados. La calidad del software no se consigue solo con la programación, sino también con una validación estructurada y repetible.

Las pruebas pueden clasificarse según varios criterios.

### 2.1. Según el momento de ejecución

- Pruebas estáticas: se realizan sin ejecutar el programa. Ejemplos: revisión de código, análisis estático, inspección de requisitos.
- Pruebas dinámicas: se ejecuta el sistema para observar su comportamiento real ante entradas concretas.

### 2.2. Según la caja de prueba

- Caja blanca: se conoce la estructura interna del código y se prueba el flujo de ejecución, decisiones y rutas lógicas.
- Caja negra: se valida solo la relación entrada-salida del sistema, sin estudiar la implementación interna.
- Caja gris: combina ambos enfoques, permitiendo conocimiento parcial del código y pruebas funcionales más profundas.

### 2.3. Según el nivel de prueba

1. Pruebas unitarias
   - Validan unidades o componentes individuales.
   - Se suelen ejecutar con pruebas automatizadas y de forma repetitiva.

2. Pruebas de integración
   - Verifican la interacción entre módulos o componentes.
   - Se comprueba que las interfaces y la interoperabilidad funcionan correctamente.

3. Pruebas de sistema
   - Se evalúa el sistema completo como conjunto.
   - Se comprueba que cumple requisitos funcionales y no funcionales.

4. Pruebas de aceptación
   - Las realiza el usuario final o el cliente.
   - Validan si la solución satisface las necesidades del negocio.

### 2.4. Según su objetivo

- Pruebas funcionales: verifican que el sistema realiza lo que debe hacer.
- Pruebas de seguridad: detectan vulnerabilidades y fallos de protección.
- Pruebas de rendimiento: analizan velocidad, escalabilidad y estabilidad.
- Pruebas de usabilidad: evalúan la facilidad de uso y la experiencia del usuario.
- Pruebas de regresión: aseguran que cambios recientes no rompen funcionalidad existente.

## 3. Pruebas de rendimiento, carga, estrés y penetración

### 3.1. Pruebas de rendimiento

Estas pruebas evalúan la capacidad del sistema para responder en tiempo razonable bajo condiciones normales y críticas. Incluyen:

- tiempo de respuesta;
- escalabilidad;
- estabilidad del sistema;
- consumo de recursos.

### 3.2. Pruebas de carga

La prueba de carga comprueba cómo se comporta el sistema cuando recibe un volumen de usuarios o transacciones cercano al esperado. Se mide si los tiempos de respuesta y la capacidad del servicio se mantienen dentro de los límites aceptables.

### 3.3. Pruebas de estrés

La prueba de estrés lleva el sistema más allá de sus condiciones normales para verificar su comportamiento bajo condiciones extremas, como picos de uso, saturación de recursos o fallos parciales.

Se busca comprobar:

- estabilidad;
- tolerancia a fallos;
- capacidad de recuperación;
- degradación controlada.

### 3.4. Pruebas de penetración

Las pruebas de penetración o pentesting simulan ataques reales para detectar vulnerabilidades explotables. Son especialmente relevantes en sistemas que gestionan información sensible, como datos sanitarios, de usuarios o financieros.

### 3.5. Herramientas de automatización de pruebas de rendimiento

Para automatizar estas pruebas se usan herramientas como Apache JMeter, Gatling o k6. En entornos modernos, estas pruebas se integran en pipelines de CI/CD para detectar regresiones de rendimiento de forma continua.

Esto es clave porque una aplicación puede funcionar bien en un entorno controlado y fallar cuando se despliega en producción con carga real.

## 4. Formación del equipo y participantes en la construcción del sistema

El éxito del proyecto depende no solo de la tecnología, sino también de la formación del equipo y de la correcta distribución de responsabilidades.

### 4.1. Formación necesaria

El equipo debe contar con capacidad en:

- metodologías de desarrollo;
- lenguajes y frameworks;
- bases de datos;
- arquitectura de software;
- gestión de proyectos;
- pruebas automatizadas;
- seguridad y despliegue.

### 4.2. Participantes relevantes

- Desarrolladores: crean y mantienen el código.
- QA/Testers: diseñan y ejecutan pruebas.
- Analistas de sistemas: validan requisitos y diseño funcional.
- Product Owner: prioriza necesidades y valora valor de negocio.
- Técnicos de sistemas: gestionan entornos, despliegues y configuración técnica.

## 5. Participantes en la construcción del sistema según MÉTRICA v3

La metodología MÉTRICA v3 es la referencia en la Administración pública española para la construcción y mantenimiento de sistemas de información.

En el proceso de Construcción del Sistema de Información (CSI), se definen una serie de actividades con roles asignados. Este es un punto muy importante para la oposición, porque se suele preguntar qué papel desempeña cada perfil en cada etapa.

### 5.1. Actividades del proceso CSI

- CSI 1: preparación del entorno de generación y construcción
- CSI 2: generación del código de los componentes y procedimientos
- CSI 3: ejecución de pruebas unitarias
- CSI 4: ejecución de pruebas de integración
- CSI 5: ejecución de pruebas del sistema
- CSI 6: elaboración de manuales de usuario
- CSI 7: definición de la formación de usuarios finales
- CSI 8: construcción de migración y carga inicial de datos
- CSI 9: aprobación del sistema de información

### 5.2. Papel del técnico de sistemas

El técnico de sistemas participa en la preparación de entornos y en tareas técnicas de soporte, especialmente en:

- preparación del entorno;
- configuración de sistemas;
- procedimientos de operación;
- seguridad;
- despliegues y migraciones.

Sin embargo, no suele intervenir directamente en:

- codificación de componentes de negocio;
- redacción de manuales de usuario;
- formación final a usuarios;
- aprobación final del sistema.

Este detalle es clave para responder preguntas de tipo “¿quién participa en tal actividad?”

## 6. Métodos y técnicas de construcción de software

### 6.1. Métodos de desarrollo

Los métodos más relevantes son:

- Desarrollo ágil: Scrum, Kanban, XP.
- Desarrollo tradicional: cascada, modelo en V.
- Desarrollo basado en componentes (CBD): reutilización de módulos y servicios.

### 6.2. Técnicas de desarrollo y prueba

- Refactorización: mejora del código sin cambiar su comportamiento externo.
- Integración continua (CI): automatización de compilación y validación del software.
- Entrega continua (CD): despliegue automatizado de cambios validados.
- TDD: desarrollo guiado por pruebas, escribiendo primero la prueba y luego el código.
- BDD: desarrollo centrado en el comportamiento esperado del sistema.

## 7. Web Components

Los Web Components son un conjunto de estándares web que permite crear elementos HTML reutilizables y encapsulados. Se basan en conceptos como:

- Custom Elements;
- Shadow DOM;
- HTML Templates;
- ES Modules.

### 7.1. Objetivos del estándar

Los objetivos propios del estándar son:

- encapsulación;
- aislamiento;
- interoperabilidad;
- reutilización.

La facilidad de uso o la experiencia de usuario no es el objetivo directo del estándar; es una consecuencia del buen diseño del componente.

### 7.2. Ventaja clave

Un componente puede desarrollarse una sola vez y reutilizarse en distintas aplicaciones o frameworks, evitando duplicación de lógica y estilos.

## 8. Atomic Design

Atomic Design es una metodología de diseño de interfaces basada en la composición jerárquica de componentes. El modelo establece varios niveles:

- átomos: elementos básicos;
- moléculas: agrupaciones pequeñas con sentido funcional;
- organismos: bloques más complejos de interfaz;
- plantillas: estructura de página;
- páginas: instancias concretas con contenido real.

Se recomienda en entornos corporativos para mantener consistencia visual y una base de diseño reutilizable. En el SAS, la STIC recomienda este enfoque frente a paradigmas como Material Design o BEM, porque Atomic Design organiza el diseño como un sistema de componentes y no como una guía de estilo aislada.

## 9. Reutilización de componentes software

La reutilización consiste en aprovechar código, servicios, módulos o bibliotecas ya desarrollados para reducir costes y tiempos de implementación.

### 9.1. Formas de reutilización

- reutilización de código fuente;
- reutilización de componentes;
- reutilización de servicios y APIs;
- uso de bibliotecas y frameworks;
- creación de líneas de producto con arquitectura común.

### 9.2. Ventajas

- reducción de costes y tiempos de desarrollo;
- menor probabilidad de errores al usar software probado;
- mayor interoperabilidad;
- mejor mantenibilidad;
- uso de estándares ya definidos.

### 9.3. Inconvenientes

- dificultad para localizar o adaptar componentes;
- dependencia de proveedores o bibliotecas externas;
- aumento del coste de mantenimiento si no se dispone del código fuente;
- posible resistencia interna a reutilizar trabajo ajeno.

### 9.4. Factores críticos de éxito en CBD

La reutilización de componentes funciona mejor cuando se cumplen estos factores:

- estándares de codificación estrictos;
- interfaces bien definidas;
- repositorio de componentes documentado;
- proceso de desarrollo orientado a la reutilización.

## 10. Claves para examen

### 10.1. Diferencias clave

- Pruebas estáticas vs dinámicas
- Caja blanca vs caja negra vs caja gris
- Pruebas unitarias vs integración vs sistema vs aceptación
- Carga vs estrés vs rendimiento
- Web Components: encapsulación, aislamiento, interoperabilidad, reutilización
- Atomic Design: enfoque de composición modular
- Reutilización: mejora productividad, pero exige disciplina y estándares

### 10.2. Conceptos repetidos en los exámenes

- El técnico de sistemas participa en la preparación de entornos y operaciones, no en manuales ni aprobación final.
- La prueba de caja gris combina conocimiento parcial de la estructura interna con evaluación funcional.
- La reutilización de componentes reduce tiempos y costes, pero requiere interfaces claras y documentación.
- Las pruebas de estrés y carga son pruebas de rendimiento, pero con objetivos distintos.
- La investigación y validación continua son esenciales para la construcción de sistemas de información.

## 11. Conclusión

La construcción de sistemas de información requiere una combinación de disciplina técnica, formación adecuada y organización del trabajo. La calidad final no depende solo del desarrollo, sino también de la prueba sistemática, la validación del comportamiento real, la coordinación de roles y la reutilización inteligente de componentes.

Por ello, los sistemas de información deben construirse con un enfoque integrado:

- pruebas bien planificadas;
- roles claros definidos en MÉTRICA v3;
- metodologías adecuadas;
- reutilización de software y componentes;
- calidad, seguridad y mantenimiento como objetivos permanentes.

En la oposición, la clave es comprender no solo las definiciones aisladas, sino la lógica que conecta pruebas, roles, procesos y reutilización dentro de la construcción del sistema.
