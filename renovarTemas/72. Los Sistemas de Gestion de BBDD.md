# **1. Introducción a los SGBD** 

Un **Sistema de Gestión de Bases de Datos (SGBD)** es un conjunto de programas que permiten definir, manipular, administrar y controlar el acceso a una base de datos de manera eficiente. Su objetivo principal es garantizar la integridad, seguridad y disponibilidad de los datos, permitiendo que múltiples usuarios y aplicaciones interactúen con ellos de forma concurrente. 

Los SGBD han evolucionado significativamente desde los primeros sistemas centralizados hasta arquitecturas distribuidas y federadas, incorporando modelos avanzados de datos y nuevas tecnologías para mejorar el rendimiento y la escalabilidad. 

# **1.1 Denominación y siglas** 

En inglés se denomina **DBMS (DataBase Management System)** , que en castellano se traduce como **Sistema Gestor (o Administrador) de Bases de Datos (SGBD)** . En la literatura también aparece como «Data Management System». Cuando el sistema sigue el modelo relacional se habla de **RDBMS / SGBDR** , y si es orientado a objetos de **OODBMS / SGBDOO** . 

# **1.2 Componentes y funciones de un SGBD** 

Un SGBD es un tipo de software muy específico que actúa como **interfaz entre las bases de datos y las aplicaciones y usuarios** que las utilizan. Se compone de: 

- **Lenguaje de Definición de Datos (DDL)** : crea y modifica la estructura (CREATE, ALTER, DROP, TRUNCATE). 

- **Lenguaje de Manipulación de Datos (DML)** : inserta, modifica y borra datos (INSERT, UPDATE, DELETE, MERGE). 

- **Lenguaje de consulta** : recupera información (SELECT). En SQL se suele incluir dentro del DML. 

- Además: **DCL** (control de acceso: GRANT, REVOKE) y **TCL** (control de transacciones: COMMIT, ROLLBACK, SAVEPOINT). 

Funciones principales (según Codd): atender peticiones de **definición** de datos; atender peticiones de **manipulación** de datos; mantener un **diccionario de datos** (catálogo con los metadatos) accesible a los usuarios; soporte de **transacciones** , **recuperación** ante fallos y **control de concurrencia** ; servicios de **autorización/seguridad** y de **integridad** ; independencia de datos; utilidades de administración (carga, copias, estadísticas). 

Importante: el SGBD **aplica y hace cumplir** las reglas de seguridad e integridad que se le declaran, pero **no define las políticas** de seguridad e integridad; estas las establece 

la organización y las implanta el DBA. Por eso «definir las políticas de seguridad e integridad» no es una función del SGBD. 

# **1.3 Tipos de usuarios de las bases de datos** 

- **Usuario final** : utiliza los datos a través de aplicaciones; ve los datos convertidos en información. Pueden ser paramétricos (usan transacciones predefinidas), casuales (consultas ocasionales) o sofisticados (analistas que lanzan consultas propias). 

- **Desarrollador / programador de aplicaciones** : desarrolla los sistemas que interactúan con la base de datos (usando SQL, APIs, ORM…). 

- **Administrador de la Base de Datos (DBA)** : asegura la integridad, consistencia, control de la redundancia y seguridad; realiza el mantenimiento diario o periódico (copias, rendimiento, usuarios y permisos, espacio). 

- **Diseñador de la base de datos** : define la estructura (modelo conceptual y lógico) antes de su implantación. 

# **1.4 SGBD más utilizados, licencias y herramientas cliente** 

**SGBD comerciales** : Oracle Database, Microsoft SQL Server, IBM Db2. **SGBD de código abierto** : MySQL (licencia GPL, con edición comercial de Oracle), MariaDB, PostgreSQL, SQLite (dominio público, embebido en la aplicación), Apache HBase y Apache Cassandra (licencia Apache 2.0), Neo4j (edición Community). Por tanto, MySQL, PostgreSQL y Apache HBase son todos de código abierto. 

Hay que distinguir el SGBD (el motor que almacena y gestiona los datos) de las **herramientas cliente** , que solo se conectan a él para consultar o administrar y **no son SGBD** : 

- **DBeaver** : cliente universal multiplataforma (JDBC) para trabajar con casi cualquier SGBD. 

- **SQuirreL SQL Client** : cliente SQL gráfico escrito en Java que se conecta vía JDBC a cualquier base de datos. Se usa para ejecutar consultas, analizar tablas y hacer tareas de mantenimiento. Ejemplo típico en sanidad: conectarse a la base de datos de **Mirth Connect** (motor de integración HL7, hoy NextGen Connect) para analizar las tablas de mensajes y su crecimiento o hacer depuraciones. Los canales y sus transformaciones JavaScript no se deben modificar tocando directamente las tablas, sino desde el Administrator o la API de Mirth. 

- **Oracle** : SQL*Plus, SQLcl, SQL Developer, Oracle Enterprise Manager (ver apartado 9). 

- **SQL Server Management Studio (SSMS)** : herramienta gráfica habitual para administrar SQL Server. 

- **pgAdmin** (PostgreSQL), **MySQL Workbench** (MySQL/MariaDB), **Toad** , **Oracle Forms** (herramienta de desarrollo de aplicaciones, no de administración). 

# **2. Modelos y Arquitecturas de Bases de Datos** 

Los modelos y arquitecturas de bases de datos definen la estructura, organización y distribución de los datos en los sistemas informáticos. 

# **2.1 Modelos de Bases de Datos** 

Existen diversos modelos de bases de datos que se utilizan dependiendo de los requisitos del sistema: 

# **Bases de Datos Relacionales (RDBMS)** 

- Basadas en el modelo relacional propuesto por **Edgar F. Codd** en 1970. 

- **Estructura:** Organizan los datos en tablas compuestas por filas y columnas, donde cada fila representa un registro y cada columna un atributo del registro. 

- **Integridad:** Utilizan claves primarias para identificar de manera única cada registro y claves foráneas para establecer relaciones entre tablas, garantizando la integridad referencial. 

- **Consultas:** Emplean el Lenguaje de Consulta Estructurado (SQL) para la gestión y manipulación de datos. 

- Ejemplos: **MySQL, PostgreSQL, Oracle Database, Microsoft SQL Server** . 

**Modelo objeto-relacional (SGBDOR)** : extiende el relacional con características de orientación a objetos (tipos definidos por el usuario, herencia de tablas, métodos, arrays). **PostgreSQL** se define como SGBD **objeto-relacional** , por lo que en los exámenes suele considerarse la opción «orientada a objetos» frente a Oracle o SQL Server (clásicamente relacionales, aunque también incorporan extensiones de objetos) y Apache HBase (NoSQL columnar). 

# **Bases de Datos No Relacionales (NoSQL)** 

Diseñadas para manejar grandes volúmenes de datos no estructurados o semiestructurados con escalabilidad y flexibilidad. Se clasifican en: 

1. **Clave-Valor** : Datos almacenados como pares clave-valor, permitiendo accesos rápidos. Ejemplo: **Redis, DynamoDB** . 

2. **Documentales** : Almacenan datos en formato JSON, BSON o XML, facilitando estructuras de datos más complejas. Ejemplo: **MongoDB, CouchDB** . 

3. **Orientadas a Objetos** : Basadas en el paradigma de POO, almacenan objetos y relaciones. Ejemplo: **db4o, ObjectDB** . 

4. **Grafos** : Optimizadas para representar y consultar relaciones complejas entre datos, utilizando nodos y aristas. Ejemplo: **Neo4j, ArangoDB** . 

5. **Columnares** : Almacenan datos por columnas en vez de filas, optimizando el rendimiento de y las operaciones analíticas. Ejemplo: **Apache Cassandra, HBase** . 

**NoSQL frente a relacional en entornos Big Data** 

- **Escalabilidad horizontal (scale-out)** : los sistemas NoSQL están diseñados para repartir datos y carga entre muchos servidores (sharding, particionado), lo que permite crecer añadiendo nodos baratos. Los relacionales tradicionales dependen principalmente de la **escalabilidad vertical (scale-up)** : un servidor más potente, lo que es limitado y costoso. 

- Manejan datos **estructurados, semiestructurados y no estructurados** con **esquema flexible** (schema-less). 

- Suelen primar disponibilidad y rendimiento frente a consistencia estricta, siguiendo el modelo **BASE** (Basically Available, Soft state, Eventual consistency) en lugar de ACID. 

# **Teorema CAP** 

Formulado por Eric Brewer (2000): un sistema distribuido no puede garantizar simultáneamente **Consistencia** (todas las réplicas devuelven el último dato escrito), **Disponibilidad** (toda petición recibe respuesta) y **Tolerancia a particiones** (el sistema sigue funcionando aunque se corte la comunicación entre nodos). Ante una partición de red hay que elegir entre C y A: 

- **Sistemas AP** (p. ej. Cassandra, DynamoDB, CouchDB): siguen respondiendo, pero ofrecen **consistencia eventual** , por lo que algunas lecturas pueden devolver temporalmente datos no actualizados. 

- **Sistemas CP** (p. ej. HBase, MongoDB en su configuración habitual): mantienen la consistencia a costa de rechazar o retrasar peticiones durante la partición. 

# **Bases de datos documentales (MongoDB): particularidades** 

- **Integridad referencial** : MongoDB no tiene claves foráneas. Si se guardan referencias entre colecciones (por _id) sin transacciones ni validaciones adicionales, **no existe integridad referencial automática nativa** comparable a una FK: se pueden borrar documentos referenciados dejando referencias huérfanas. La integridad debe garantizarla la aplicación (validaciones $jsonSchema, transacciones multidocumento desde la versión 4.0, $lookup solo sirve para consultar). 

- Sí admite **índices secundarios** y **compuestos** , y documentos con **arrays y subdocumentos anidados** . Con índices adecuados no es necesario recorrer toda la colección. 

- **Índices multikey y consultas sobre arrays** : un índice sobre campos de un array de subdocumentos (p. ej. {"lineas.producto": 1, "lineas.precio": 1}) es multikey. Una consulta como find({"lineas.producto": "X", "lineas.precio": {$gt: 15}}) **puede devolver documentos en los que una línea cumpla producto = "X" y otra línea distinta cumpla precio > 15** . Para exigir que ambas condiciones se cumplan en el **mismo elemento** del array hay que usar **$elemMatch** : find({lineas: {$elemMatch: {producto: "X", precio: {$gt: 15}}}}). El índice compuesto no cambia esa semántica de la consulta. 

**Bases de datos columnares frente a orientadas a fila** 

- Almacenan juntos los valores de cada columna, lo que permite una **gran compresión** (menor ocupación en disco) y **lecturas más rápidas** en consultas analíticas que agregan pocas columnas sobre muchas filas (OLAP, data warehouse). 

- Son **más lentas en la escritura** de registros individuales (cada fila se reparte en varias columnas) y **no están indicadas para entornos con muchas transacciones** (OLTP), donde son mejores las orientadas a fila. 

# **Bases de datos orientadas a objetos (SGBDOO): detalle** 

Integran el paradigma de la programación orientada a objetos en la base de datos. Características: 

- **Encapsulamiento** , **herencia** , **polimorfismo** , tipos complejos y definidos por el usuario. 

- **Identidad de objeto (OID)** : cada objeto tiene un identificador único, generado por el sistema e independiente de sus valores. 

- **Relaciones** : no se implementan con claves foráneas, sino **incluyendo en cada objeto los identificadores (OID/referencias) de los objetos con los que se relaciona** . 

- **No utilizan SQL** : el estándar **ODMG** define **ODL (Object Definition Language)** para definir los objetos (equivale al DDL), **OQL (Object Query Language)** para consultarlos y **OML** para manipularlos. 

- Modelo más adecuado para datos complejos como **Sistemas de Información Geográfica (SIG)** , CAD/CAM o multimedia. 

- Ejemplos: db4o, ObjectDB, Versant, ObjectStore. 

# **Desajuste de impedancia y motor de persistencia (ORM)** 

Entre el modelo de objetos de la programación (OOP) y el modelo relacional existe un **desajuste de impedancia** (objetos, herencia y referencias frente a tablas, filas y claves). Para que interactúen con eficacia se necesita una **capa de programación que actúe como «traductor»** : el **motor de persistencia** u **ORM (Object-Relational Mapping)** , que traduce los objetos a filas de la BD y viceversa. Ejemplos: Hibernate y JPA (Java), Entity Framework (.NET), Doctrine y Eloquent (PHP), SQLAlchemy (Python). Por tanto, sí se puede usar OOP con una BD relacional; no es necesaria una BD orientada a objetos. 

# **2.2 Arquitecturas de Bases de Datos** 

Las bases de datos pueden organizarse bajo diferentes arquitecturas: 

1. **Bases de Datos Centralizadas** 

   - Toda la información reside en un solo servidor central. 

   - Facilita la administración y seguridad, pero presenta problemas de escalabilidad y rendimiento. 

- Mayor riesgo de fallo único. 

# 2. **Bases de Datos Distribuidas** 

- Los datos están replicados o fragmentados en múltiples nodos o servidores. 

- Pueden ser **homogéneas** (mismo SGBD) o **heterogéneas** (diferentes SGBD). 

- Mejora la disponibilidad y rendimiento, pero aumenta la complejidad. 

- Mayor tolerancia a fallos y escalabilidad. 

- Requiere mecanismos de sincronización complejos. 

# 3. **Bases de Datos Federadas** 

- Permiten que diferentes bases de datos autónomas e independientes trabajen juntas sin integrarse físicamente en un solo sistema. 

- Cada base de datos mantiene su autonomía, pero coopera bajo un esquema federado para operaciones globales. 

- Útil en entornos empresariales donde se necesita interoperabilidad sin migraciones. 

- Ejemplo: red de hospitales con bases de datos separadas pero accesibles globalmente. 

**Clasificación de los sistemas federados (Sheth y Larson)** según quién gestiona la federación: 

- **Fuertemente acoplados** : existe un **administrador de la federación** que tiene todo el control sobre su creación y mantenimiento y sobre el acceso a las bases de datos componentes. Soportan **uno o más esquemas federados** definidos de forma centralizada. 

- **Débilmente acoplados** : **los propios usuarios son los responsables de crear y mantener las federaciones** , normalmente mediante la definición de **vistas** sobre las bases de datos componentes; no existe un control ni un esquema federado global gestionado por un administrador. 

# **2.3 Escalabilidad y alta disponibilidad** 

**Escalabilidad** es la capacidad de un sistema para manejar volúmenes crecientes de datos, usuarios y operaciones concurrentes sin degradar su rendimiento, añadiendo recursos. 

- **Vertical (scale-up)** : mejorar un único servidor añadiendo CPU, RAM o almacenamiento más rápido. Sencilla, pero con límite físico y coste creciente. Ej.: actualizar el servidor de imágenes médicas con procesadores y discos más potentes. 

- **Horizontal (scale-out)** : añadir más servidores para distribuir la carga. Ej.: un sistema de teleconsulta que añade nodos para atender más consultas simultáneas. 

- **Elástica / automática (cloud)** : los recursos crecen y decrecen automáticamente según la demanda (p. ej. una plataforma de análisis genómico que amplía capacidad durante un proyecto y la reduce después para ahorrar costes). 

- No es escalabilidad el **ajuste manual** (optimizar consultas, añadir índices) cada vez que el sistema se degrada: eso es tuning u optimización de rendimiento. 

# **Arquitecturas de alta disponibilidad** : 

- **Activo-Pasivo** : un nodo da servicio y otro espera en reserva (standby) para tomar el control si el primero falla (p. ej. Oracle Data Guard). 

- **Activo-Activo** : dos o más nodos dan servicio simultáneamente sobre los mismos datos. Lo permiten, entre otros, **Oracle Real Application Clusters (RAC)** (varias instancias sobre una misma base de datos en almacenamiento compartido, sincronizadas por Cache Fusion), **MySQL** (Group Replication/InnoDB Cluster en modo multiprimario, MySQL NDB Cluster) y **MariaDB** (Galera Cluster, multimaestro síncrono). Por tanto, cualquiera de los tres puede cumplir un requisito activo+activo. 

- **Requisito clave del activo-activo** : una **comunicación entre nodos con latencia muy baja** (interconexión privada dedicada), ya que los nodos deben sincronizar bloqueos y datos de forma continua; con latencia alta el rendimiento cae y aparecen fallos de servicio. Por eso los clúster activo-activo extendidos entre CPDs solo son viables a distancias cortas. No existe un ancho de banda mínimo fijo (como 10 Gbps) exigido con carácter general. 

- **Clasificación Tier de CPD (Uptime Institute)** : Tier I (básico, ~99,671 %), Tier II (componentes redundantes, ~99,741 %), Tier III (mantenimiento concurrente, ~99,982 %) y Tier IV (tolerante a fallos, ~99,995 %). Un Tier I no aporta redundancia, por lo que no es un requisito para un servicio activo-activo (de hecho, sería insuficiente). Una disponibilidad del 99,99 % equivale a unos 52 minutos de parada al año. 

# **3. Motores de Indexación** 

Los motores de indexación permiten mejorar el rendimiento de las consultas en las bases de datos mediante estructuras de búsqueda optimizadas: 

- **Árboles B+** : Estructuras de datos en forma de árbol equilibrado que permiten búsquedas, inserciones y eliminaciones eficientes, ampliamente utilizadas en bases de datos relacionales. 

- **Hashing** : Utiliza funciones hash para mapear claves a posiciones específicas en una tabla hash, facilitando accesos directos y rápidos. 

- **Índices Bitmap** : Utilizan vectores de bits para representar la existencia de valores específicos en un conjunto de datos, optimizando consultas en columnas con pocos valores distintos. 

**Criterio de cardinalidad** : los índices **B-tree** son adecuados para columnas de **alta cardinalidad** (muchos valores distintos, p. ej. DNI o NHC). Los índices **bitmap** son adecuados para columnas de **baja cardinalidad** (sexo, estado, provincia) en entornos de consulta/data warehouse; no conviene usarlos en tablas OLTP con muchas actualizaciones concurrentes, porque bloquean muchas filas a la vez. 

# **3.1 Optimización del rendimiento** 

- **No indexar todas las columnas** : cada índice acelera las lecturas pero ralentiza INSERT/UPDATE/DELETE y ocupa espacio. Se indexan las columnas usadas en filtros, uniones y ordenaciones. 

- **Desnormalización controlada** : introducir redundancia calculada (columnas derivadas, tablas resumen, vistas materializadas) para reducir uniones y la complejidad de las consultas más frecuentes. 

- Mantener **estadísticas** actualizadas para el optimizador, revisar los **planes de ejecución** , ajustar los **parámetros de inicialización** de la instancia (memoria SGA/PGA, etc.) y usar particionado en tablas muy grandes. 

# **3.2 Optimizador de consultas y plan de ejecución** 

El **plan de ejecución** es el conjunto de pasos que describe **cómo el SGBD (p. ej. Oracle) procesará una consulta** : orden de acceso a las tablas, uso de índices o recorridos completos (full scan), métodos de unión (nested loops, hash join, merge join) y coste estimado. Lo genera el **optimizador basado en costes (CBO)** y es esencial para diagnosticar y optimizar el rendimiento de las consultas. No es código PL/SQL, ni una copia de seguridad, ni un índice. 

- En Oracle se consulta con **EXPLAIN PLAN FOR <sentencia>** y DBMS_XPLAN.DISPLAY, con AUTOTRACE en SQL*Plus o gráficamente en SQL Developer. Históricamente Oracle Enterprise Manager incluía la herramienta **SQL Analyze** (Tuning Pack) para analizar el explain plan. 

- **HINT** : comentario especial incluido en la sentencia SQL con la sintaxis /*+ ... */ que **modifica o dirige la decisión del optimizador** (p. ej. SELECT /*+ INDEX(p idx_nhc) */ ... fuerza el uso de un índice). 

# **4. Modelo de Referencia ANSI/SPARC** 

Este modelo conceptual define una arquitectura de tres niveles: 

1. **Nivel Externo** : Define cómo los usuarios visualizan los datos mediante vistas personalizadas (diferentes usuarios con diferentes vistas). Muestran a cada usuario solo la información relevante para el y oculta el resto. 

2. **Nivel Conceptual** : Describe la estructura lógica global de la base de datos (tablas, relaciones, restricciones), independiente de las consideraciones físicas. 

3. **Nivel Interno** : Describe cómo se almacenan físicamente los datos en el sistema, incluyendo estructuras de almacenamiento y métodos de acceso. 

Este diseño proporciona **independencia lógica y física de datos** , facilitando cambios estructurales sin afectar a los usuarios y que los cambios en un nivel no afecten directamente a otros. 

**Modelo de referencia ANSI/X3/SPARC (1975-1978)** : además de los tres niveles, define los componentes y las interfaces del SGBD y los perfiles de administración (administrador de la empresa, de la base de datos y de aplicaciones). Su elemento central es el **diccionario de datos** , que almacena los metadatos: las definiciones de los esquemas externo, conceptual e interno y las correspondencias entre ellos. Por tanto, la definición de un dato como de tipo «integer» se encuentra en el **Diccionario de Datos** (no en el núcleo, ni en el esquema de tabla, ni en la capa de aplicación). 

Las **correspondencias (mappings)** externo/conceptual y conceptual/interno son las que proporcionan, respectivamente, la independencia lógica y la independencia física. 

# **5. Monitor de Transacciones** 

El monitor de transacciones gestiona la ejecución de transacciones, asegurando que cumplan con las propiedades **ACID** : 

- **Atomicidad** : Una transacción se ejecuta completamente o no se ejecuta. 

- **Consistencia** : La base de datos permanece en un estado válido antes y después de la transacción manteniendo la integridad. Las transacciones llevan el sistema de un estado consistente a otro. 

- **Aislamiento** : Cada transacción se ejecuta sin interferencias de otras. La ejecución de una transacción no debe verse afectada por otras transacciones concurrentes (el resultado debe ser equivalente a ejecutarlas de forma serie). 

- **Durabilidad** : Una vez completada, la transacción es permanente, incluso en caso de fallos. Los cambios confirmados persisten incluso en caso de fallos. 

**Comandos SQL de control de transacciones (TCL)** : 

- **COMMIT** : finaliza la transacción y hace **permanentes** sus cambios (Durabilidad). 

- **ROLLBACK** : deshace los cambios no confirmados de la transacción (o hasta un savepoint con ROLLBACK TO). 

- **SAVEPOINT** : marca un punto intermedio dentro de la transacción al que se puede volver sin deshacerla entera. 

- **SET TRANSACTION** : establece propiedades como el nivel de aislamiento o solo lectura. 

- **TRUNCATE** no es un comando de transacción sino DDL: vacía una tabla y, en Oracle, realiza un COMMIT implícito (no se puede deshacer con ROLLBACK). 

Ejemplos de **monitores de transacciones (TP monitors)** comerciales: IBM CICS, Oracle Tuxedo, Microsoft Transaction Server/COM+. 

# **6. Control de Concurrencia y Bloqueos** 

La concurrencia permite que múltiples usuarios accedan a la base de datos simultáneamente. Para evitar conflictos, se utilizan mecanismos de bloqueo: 

1. **Bloqueo Exclusivo (X)** : Solo una transacción a la vez puede modificar un dato, evitando conflictos de escritura. 

2. **Bloqueo Compartido** : Varias transacciones pueden leer, pero no modificar mientras exista un bloqueo compartido. 

3. **Protocolo de Bloqueo en Dos Fases (2PL)** : 

   - **Fase de expansión** : Adquiere bloqueos sin liberarlos. 

   - **Fase de contracción** : Libera bloqueos y no adquiere más. 

4. Bloqueo Pesimista: evita conflictos con bloqueos (ver detalle más abajo) 

5. Bloqueo Optimista: permite acceso sin bloqueos, validando cambios antes de confirmar. 

Estos mecanismos previenen problemas como: 

- **Condiciones de carrera** : Cuando varias transacciones intentan modificar el mismo dato simultáneamente. 

- **Deadlocks** : Ocurre cuando dos o más transacciones esperan mutuamente por recursos bloqueados. 

# **6.1 Control pesimista frente a optimista** 

- **Pesimista** : asume que habrá conflictos y **bloquea el registro en cuanto el usuario lo selecciona para actualizarlo** (antes de modificarlo), p. ej. con SELECT ... FOR UPDATE. Garantiza que nadie más lo modifique, pero reduce la concurrencia y puede provocar esperas y deadlocks. 

- **Optimista** : no bloquea al leer; al confirmar comprueba (por número de versión o marca de tiempo) si otro usuario ha modificado el dato y, si es así, rechaza o reintenta la operación. Adecuado cuando los conflictos son poco frecuentes. 

# **6.2 Anomalías de concurrencia** 

Sin un control de bloqueos adecuado pueden aparecer: 

- **Lectura sucia (dirty read)** : una transacción lee datos modificados por otra que aún no ha hecho COMMIT (y que podría deshacerse). 

- **Lectura no repetible** : al releer una fila, sus valores han cambiado porque otra transacción la modificó y confirmó. 

- **Lectura fantasma (phantom read)** : al repetir una consulta aparecen o desaparecen filas por inserciones o borrados de otra transacción. 

- **Actualización perdida (lost update)** : dos transacciones actualizan el mismo dato y una sobrescribe los cambios de la otra. 

**Niveles de aislamiento ANSI SQL** : READ UNCOMMITTED (permite lecturas sucias), READ COMMITTED (evita lecturas sucias; nivel por defecto en Oracle y SQL Server), REPEATABLE READ (evita además lecturas no repetibles; por defecto en MySQL InnoDB) y SERIALIZABLE (evita todas las anomalías). 

# **6.3 Técnicas frente a los interbloqueos (deadlocks)** 

- **Ordenación por marcas de tiempo (timestamp ordering)** : a cada transacción se le asigna una marca de tiempo y las operaciones conflictivas se ejecutan en ese orden; como no se usan esperas por bloqueos, se **minimiza (evita) la posibilidad de deadlock** (las transacciones que violan el orden se abortan y reinician). 

- **Prevención con marcas de tiempo** : esquemas **wait-die** y **wound-wait** , que deciden si una transacción espera o se aborta según su antigüedad. 

- **Detección y resolución** : el SGBD construye un **grafo de espera** y, si detecta un ciclo, aborta una de las transacciones (víctima). Es lo que hace Oracle, que devuelve el error ORA-00060. 

- **MVCC (control de concurrencia multiversión)** : los lectores ven una versión consistente de los datos sin bloquear a los escritores (Oracle, PostgreSQL). 

- Aplicar bloqueo exclusivo a todo, esperar indefinidamente o eliminar los logs no evita deadlocks: empeora la concurrencia o compromete la recuperación. 

# **7. Recuperación de Errores** 

Los SGBD implementan estrategias para recuperar datos tras fallos: 

- **Registros de Log (WAL – Write-Ahead Logging)** : Se registran cambios antes de aplicarlos, permitiendo reversión o repetición de transacciones en caso de fallos. 

- **Checkpoints** : Estados de la base de datos almacenados periódicamente en puntos seguros para facilitar la recuperación. 

- **Shadow Paging** : Mantiene versiones antiguas de los datos hasta que se confirme una transacción. 

- **Rollback** : Se revierten los cambios no confirmados. 

Tipos de backup: 

- **Completo:** Copia de toda la base de datos. 

- **Incremental:** Solo guarda los cambios desde el último backup. 

- **Diferencial:** Copia de cambios desde el último backup completo. 

**Copias físicas y lógicas** : las **físicas** copian los ficheros de la base de datos; las **lógicas** exportan objetos y datos (en Oracle, Data Pump: expdp/impdp). Pueden ser **en frío** (base de datos parada) o **en caliente** (en funcionamiento). 

# **7.1 Recuperación en Oracle** 

- **Redo logs** : ficheros en los que Oracle registra todos los cambios (equivalen al WAL). Se escriben de forma circular en grupos. 

- **Modo ARCHIVELOG** : los redo logs llenos se **archivan** (archived redo logs) antes de reutilizarse. Permite hacer copias en caliente y **recuperar la base de datos hasta el último COMMIT** o hasta un momento concreto (point-in-time recovery). En modo **NOARCHIVELOG** solo se puede restaurar hasta la última copia completa en frío. 

- **RMAN (Recovery Manager)** : herramienta nativa de Oracle para **copias de seguridad consistentes y recuperación** (completas, incrementales, a nivel de bloque, validación de copias, catálogo de copias). Herramientas genéricas como rsync no garantizan una copia consistente de una base de datos abierta. 

- **Flashback** : permite consultar o revertir datos a un estado anterior sin restaurar copias. 

# **8. Integridad de Datos** 

La integridad garantiza que los datos sean **precisos, coherentes y confiables** . Se aplica mediante: 

1. **Integridad de Entidad** : Garantiza que cada registro tenga un identificador único (clave primaria). 

2. **Integridad Referencial** : Controla que las relaciones entre tablas sean válidas mediante claves foráneas. 

3. **Restricciones de Dominio** : Define valores permitidos en los campos. 

4. **Reglas de Negocio** : Aplican restricciones personalizadas según requerimientos específicos. 

# **9. Oracle Database y herramientas de administración** 

Oracle Database es el SGBD relacional más extendido en la Administración y en el SAS. Conceptos básicos: 

- **Instancia y base de datos** : la instancia es el conjunto de estructuras de memoria (SGA, PGA) y procesos en segundo plano; la base de datos es el conjunto de ficheros físicos (datafiles, control files, redo logs). 

- **Tablespace** : unidad **lógica** de almacenamiento que agrupa uno o varios ficheros físicos de datos (datafiles). Sirve para organizar dónde se guardan tablas, índices y demás segmentos. Ejemplos: SYSTEM, SYSAUX, UNDO, TEMP, USERS. 

- **Listener** : **proceso de red que escucha las peticiones de conexión de los clientes** a la base de datos y las pasa a la instancia. Se configura en listener.ora; en el cliente, los alias de conexión se definen en tnsnames.ora. 

- **Puerto por defecto del listener: 1521/TCP** . Es el puerto que habría que abrir en un cortafuegos entre un servidor de aplicaciones y un servidor Oracle en otra 

VLAN. Otros puertos por defecto: SQL Server 1433, MySQL/MariaDB 3306, PostgreSQL 5432, MongoDB 27017; el 8080 es un puerto HTTP alternativo habitual en servidores de aplicaciones. 

**Herramientas de Oracle** : 

- **SQL*Plus** : herramienta de línea de comandos para ejecutar SQL y PL/SQL de forma **interactiva o mediante scripts** . SQLcl es su versión moderna. 

- **SQL Developer** : entorno gráfico gratuito de desarrollo y administración. 

- **Oracle Enterprise Manager (OEM)** : consola de administración y monitorización. 

- **RMAN** (copias y recuperación) y **Data Pump** (exportación e importación lógica). 

- **Oracle APEX (Application Express)** : plataforma low-code sobre la base de datos. Sus módulos principales son **App Builder** (crear aplicaciones), **SQL Workshop** (donde **se gestionan los objetos de la base de datos** : Object Browser, SQL Commands, SQL Scripts, utilidades de carga de datos, servicios REST), **Team Development** (seguimiento de funcionalidades e incidencias) y **Gallery** (aplicaciones de ejemplo). 

**Configuración regional (globalización / NLS)** : Oracle define la configuración regional mediante parámetros NLS: NLS_CHARACTERSET (juego de caracteres de la BD, p. ej. AL32UTF8 o WE8ISO8859P15, este último ISO-8859-15 con soporte del símbolo €), NLS_LANGUAGE, NLS_TERRITORY, NLS_NUMERIC_CHARACTERS (separador decimal y de miles), NLS_CURRENCY (símbolo de moneda) y NLS_DATE_FORMAT. En una base de datos de la Administración española lo coherente con la normativa es territorio España, **coma como separador decimal** y **euro (€) como moneda** ; por eso una configuración con el **dólar ($)** como moneda sería un incumplimiento. Las herramientas de revisión de calidad de BBDD de la Oficina de Calidad de la STIC comprueban este tipo de parámetros junto con el uso de tipos de datos soportados.
