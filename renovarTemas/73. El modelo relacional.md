# **0. Introducción** 

El **modelo de datos** es un conjunto de conceptos que permite describir los datos, sus relaciones y restricciones en un sistema de bases de datos. Su principal objetivo es proporcionar una representación estructurada y lógica de la información. 

Los modelos de datos se pueden clasificar en: 

- **Modelos Conceptuales:** Describen los datos con un alto nivel de abstracción, independiente del gestor de base de datos. Ejemplo: **Modelo Entidad-Relación** . 

- **Modelos Lógicos:** Representan los datos mediante estructuras de registros y dependen del tipo de base de datos utilizada. Ejemplo: **Modelo Relacional, Modelo Jerárquico, Modelo en Red** . 

- **Modelos Físicos:** Detallan la manera en que los datos se almacenan físicamente en disco, incluyendo estructuras de almacenamiento y métodos de acceso. 

# **Diseño de Bases de Datos** 

El diseño de bases de datos se divide en tres fases: 

1. **Diseño Conceptual:** Utiliza un modelo conceptual para definir los datos y sus relaciones, sin preocuparse por detalles técnicos. 

2. **Diseño Lógico:** Convierte el diseño conceptual en un esquema lógico adecuado para un SGBD (ejemplo: esquema relacional). 

3. **Diseño Físico:** Define la estructura de almacenamiento y los métodos de acceso optimizados para el rendimiento del sistema. 

# **1. Definiciones y Conceptos Básicos** 

El **modelo relacional** es un modelo lógico que estructura los datos 

en **tablas** donde cada registro es una **tupla** y cada columna un **atributo** . Se utilizan claves primarias y foráneas para establecer relaciones entre entidades. Se basa en la teoría de conjuntos y en la lógica de predicados de primer orden, principalmente en el concepto matemático de **relación** . 

Se basa en la teoría de conjuntos y en la lógica de predicados de primer orden. En este modelo, los datos se organizan en **tablas** (relaciones) donde cada fila representa una tupla y cada columna un atributo. 

# **1.1 Elementos principales del modelo relacional** 

- **Relación (tabla):** Conjunto de datos estructurados. Tabla bidimensional donde se almacenan los datos. 

   - **Características** 

      - Tiene nombre único dentro del esquema. 

      - Está compuesta por filas (tuplas) y columnas (atributos). 

      - No existen filas duplicadas. 

      - Cada atributo tiene un dominio de valores predefinido. 

      - El orden de los atributos y las tuplas no importa. 

      - **Cardinalidad** : número de tuplas que contiene. 

      - **Grado** : número de atributos que contiene. 

   - **Tipos** 

      - **Relaciones base** : tablas reales almacenadas en BBDD. 

      - **Vistas** : tablas virtuales creadas a partir de otras, sin almacenamiento propio. 

      - **Instantáneas** : relaciones derivadas almacenadas físicamente, utilizadas para consultas de solo lectura. 

      - **Resultados de consultas** : tablas temporales generadas a partir de consultas SQL. 

- 

   - **Tupla (fila):** Representa una instancia de la relación. Cada fila de la tabla. 

- **Atributo (columna):** Representa una propiedad de la relación. Cada columna de la tabla. Tiene un dominio de valores predefinido por lo que pueden ser: 

      - **Simple** : Contiene valores atómicos (Ejemplo: números enteros, cadenas de texto). 

      - **Compuesto** : Contiene estructuras complejas (Ejemplo: direcciones que combinan calle, número y código postal). 

- 

- **Claves:** Atributos que identifican de manera única cada tupla en una. 

   - **Clave primaria:** Identifica de forma única cada tupla. 

   - **Clave foránea o ajena:** Relaciona una tabla con otra. Referencia la clave primaria de otra tabla. 

   - **Claves candidatas:** conjunto de atributos que pueden servir como clave primaria. 

   - **Clave alternativa:** claves candidatas no seleccionadas como primarias. 

- **Esquema relacional:** Define la estructura de las relaciones y restricciones. 

- **Reglas de integridad:** el modelo relacional define dos fundamentales 

   - **Integridad de entidad:** clave primaria no puede contener valores nulos. 

   - **Integridad referencial:** clave foránea debe referenciar a una clave primaria existente o tomar valor nulo. 

# **1.2. Propiedades de las claves** 

**Superclave:** conjunto de uno o más atributos que identifica de forma única cada tupla de la relación (puede contener atributos superfluos). 

**Clave candidata:** superclave mínima. Debe cumplir tres propiedades: 

- **Unicidad:** no pueden existir dos tuplas con el mismo valor de la clave. 

- **Minimalidad (irreducibilidad):** si se elimina cualquiera de sus atributos deja de identificar de forma única. 

- **No nulidad:** ninguno de sus atributos puede tomar valor nulo, tanto si la clave es simple como si es compuesta. Un valor nulo no permitiría identificar la tupla, por lo que es FALSO que una clave candidata compuesta pueda contener atributos nulos. 

Una relación puede tener varias claves candidatas; se elige una como **clave primaria** y el resto pasan a llamarse **claves alternativas** . En SQL las claves alternativas suelen implementarse con restricciones UNIQUE (que en la práctica algunos SGBD permiten con nulos), pero en la teoría del modelo relacional una clave candidata nunca admite nulos. 

# **1.3. Operaciones que pueden violar la integridad referencial** 

La integridad referencial puede romperse tanto en la tabla hija (la que contiene la clave foránea) como en la tabla padre (la referenciada): 

- **INSERT** en la tabla hija de una fila cuya clave foránea no existe en la tabla padre. 

- **UPDATE** de la clave foránea en la hija (a un valor inexistente) o de la clave primaria en la padre (dejando filas hijas huérfanas). 

- **DELETE** de una fila de la tabla padre que está referenciada por filas de la tabla hija. Es el caso típico de violación de integridad referencial y el que se cita habitualmente en los exámenes, porque al borrar el registro padre las filas hijas quedan huérfanas si no se gestiona. 

- **SELECT** nunca puede violar la integridad, porque no modifica datos. 

Para gestionar estas situaciones se definen **acciones referenciales** al declarar la clave foránea (ON DELETE / ON UPDATE): 

|**Acción**|**Efecto al borrar/modificar la fila padre**|
|---|---|
|**RESTRICT / NO ACTION**|Se rechaza la operación si existen filas hijas<br>(comportamiento por defecto).|



|**CASCADE**|Se borran (o actualizan) automáticamente las filas hijas.|
|---|---|
|**SET NULL**|La clave foránea de las filas hijas pasa a valor nulo.|
|**SET DEFAULT**|La clave foránea de las filas hijas toma su valor por defecto.|



Oracle solo admite ON DELETE CASCADE y ON DELETE SET NULL (no dispone de ON UPDATE). 

```
CREATE TABLE Empleados (
  ID INT PRIMARY KEY,
  ID_Departamento INT REFERENCES Departamentos(ID) ON DELETE CASCADE
);
```

# **1.4. Restricciones diferibles (DEFERRABLE)** 

El estándar SQL (y SGBD como Oracle o PostgreSQL) permite indicar **cuándo** se comprueba una restricción dentro de una transacción: 

- **NOT DEFERRABLE** (por defecto): la restricción se comprueba inmediatamente al finalizar cada sentencia (INSERT, UPDATE, DELETE). 

- **DEFERRABLE INITIALLY IMMEDIATE:** se comprueba tras cada sentencia, pero la transacción puede aplazarla con SET CONSTRAINTS ... DEFERRED. 

- **DEFERRABLE INITIALLY DEFERRED:** la restricción solo se comprueba al hacer **COMMIT** de la transacción. Si en ese momento se incumple, el COMMIT falla y la transacción se deshace. Resulta útil para cargar tablas con referencias circulares o insertar hijos antes que padres. 

```
ALTER TABLE Empleados ADD CONSTRAINT fk_dep
  FOREIGN KEY (ID_Departamento) REFERENCES Departamentos(ID)
  DEFERRABLE INITIALLY DEFERRED;
```

# **2. Arquitectura del Modelo Relacional** 

El modelo relacional sigue la arquitectura en **tres niveles del estándar ANSI-SPARC** : 

1. **Nivel externo:** Define cómo los usuarios visualizan los datos. Define vistas y esquemas externos para usuarios específicos. 

2. **Nivel conceptual:** Representa la estructura lógica general de la base de datos, incluyendo relaciones, atributos, dominios, claves y restricciones de integridad. 

3. **Nivel interno:** Define cómo se almacenan los datos físicamente. Representación física. 

Esta arquitectura proporciona **independencia lógica y física** entre las aplicaciones y los datos. 

# **2.1. Reglas de Codd para los DBMS Relacionales** 

Edgar F. Codd formuló en 1985 un conjunto de **12 reglas** que determinan si un SGBD es verdaderamente relacional: 

1. **Representación de la Información:** Todos los datos deben almacenarse en tablas. 

2. **Acceso por Clave Primaria:** Cada dato debe ser accesible mediante su clave. 

3. **Tratamiento Sistemático de Valores Nulos:** Los valores nulos deben gestionarse de manera uniforme. 

4. **Diccionario de Datos Relacional:** La información sobre la estructura de la base de datos debe estar representada en el mismo formato que los datos. 

5. **Lenguaje Completo de Datos:** Debe existir un lenguaje que permita definir, manipular y gestionar los datos (ejemplo: SQL). 

6. **Actualización de Vistas:** Las vistas actualizables deben poder modificarse sin restricciones. 

7. **Inserciones, Modificaciones y Eliminaciones de Alto Nivel:** Debe permitirse la manipulación de conjuntos de datos mediante una sola operación. 

8. **Independencia Física de los Datos:** Los cambios en el almacenamiento físico no deben afectar a la lógica de los datos. 

9. **Independencia Lógica de los Datos:** Los cambios en el esquema lógico no deben afectar a las aplicaciones. 

10. **Independencia de la Integridad:** Las reglas de integridad deben poder definirse en el propio sistema sin depender de los programas de aplicación. 

11. **Independencia de la Distribución:** El acceso a datos distribuidos no debe requerir cambios en la lógica de las consultas. 

12. **Regla de la No Subversión:** No debe existir un acceso de bajo nivel que permita evitar las restricciones del modelo relacional. 

# **3. Diseño de Bases de Datos Relacionales** 

El diseño de bases de datos relacionales se basa en tres fases: 

1. **Modelo Conceptual:** Se representa con **el modelo entidad-relación (E-R)** . 

2. **Modelo Lógico:** Se transforma el modelo E-R en **tablas relacionales** (esquema relacional). 

3. **Modelo Físico:** Implementación en un SGBD. 

# **3.1 Modelo Entidad-Relación (E-R)** 

- **Entidades:** Representan objetos del mundo real. 

- **Atributos:** Propiedades de una entidad. 

- **Relaciones:** Asociaciones entre entidades. 

**Cardinalidad o tipo de correspondencia** de una relación binaria: indica el número máximo de ocurrencias de una entidad que pueden asociarse con una ocurrencia de la 

otra. Puede ser 1:1, 1:N o N:M (muchos a muchos). También se indican las **participaciones** (mínimo y máximo), por ejemplo (0,N) o (1,1). 

- **Entidad débil:** depende de otra (entidad fuerte) para existir o identificarse. 

- **Atributos de la relación:** propiedades que pertenecen a la asociación y no a las entidades (p. ej., la nota en la relación ALUMNO-cursa-CURSO). 

# **3.2. Transformación del modelo E/R al modelo relacional** 

Al pasar del diseño conceptual (E/R) al diseño lógico (relacional) se aplican las siguientes reglas: 

- **Cada entidad** se transforma en una tabla. Su identificador pasa a ser la clave primaria. 

- **Relación 1:1:** no genera tabla nueva. Se propaga la clave de una de las entidades como clave foránea a la otra (normalmente a la que tiene participación obligatoria). Si ambas participaciones son (1,1) pueden fusionarse en una sola tabla. 

- **Relación 1:N:** no genera tabla nueva. Se propaga la clave primaria de la entidad del lado 1 como clave foránea a la tabla del lado N. Los atributos de la relación pasan también a la tabla del lado N. (Excepción: si la participación del lado 1 es opcional (0,1) y se quieren evitar nulos, puede crearse una tabla intermedia.) 

- **Relación N:M:** siempre genera una **tabla nueva** cuya clave primaria es la composición de las claves primarias de las entidades que relaciona (que a su vez son claves foráneas). Los atributos de la relación se incluyen en esa tabla. 

- **Relaciones n-arias (ternarias, etc.):** generan una tabla con las claves de todas las entidades participantes. 

- **Entidad débil:** tabla cuya clave primaria incluye la clave de la entidad fuerte de la que depende. 

- **Jerarquías (generalización/especialización):** pueden resolverse con una única tabla para el supertipo, una tabla por subtipo, o una tabla para el supertipo y otra para cada subtipo. 

**Ejemplo:** PROFESORES (1) --imparte-- (N) CURSOS y CURSOS (N) --cursa-- (M) ALUMNOS. 

- PROFESORES, CURSOS y ALUMNOS generan una tabla cada una (3 tablas). 

- «Imparte» es 1:N, por lo que NO genera tabla: la clave de PROFESORES se propaga como clave foránea a CURSOS. 

- «Cursa» es N:M, por lo que SÍ genera tabla: CURSA(id_curso, id_alumno). 

- Resultado: **4 tablas** : Profesores, Cursos (con id_profesor como FK), Cursa y Alumnos. 

```
PROFESORES (id_profesor PK, nombre, ...)
CURSOS     (id_curso PK, titulo, ..., id_profesor FK -> PROFESORES)
ALUMNOS    (id_alumno PK, nombre, ...)
CURSA      (id_curso FK, id_alumno FK, PK(id_curso, id_alumno))
```

# **4. Normalización de Bases de Datos** 

La **normalización** reduce la **redundancia** y mejora la **integridad** mediante la aplicación de **formas normales (FN)** . Su objetivo es dividir los datos en tablas mas pequeñas vinculadas para minimizar problemas de redundancia y anomalías en la actualización. 

# **Dependencia Funcional y Determinante** 

La normalización se basa en las **dependencias funcionales** , que describen la 

relación entre los atributos de una tabla. 

- **Dependencia Funcional:** Un atributo **Y** depende funcionalmente de otro atributo **X** si, para cada valor de **X** , existe un único valor de **Y** . Se denota como: X→Y 

Ejemplo: En una tabla de empleados, si el **DNI** determina un **nombre** , entonces: 

DNI→NombreDNI 

- **Determinante:** Es el atributo o conjunto de atributos de los cuales dependen otros atributos. En el ejemplo anterior, **DNI** es el determinante de **Nombre** . 

- **Dependencia Funcional Completa:** Se da cuando un atributo depende funcionalmente de toda la clave primaria y no de una parte de ella. 

- **Dependencia Transitiva:** Se produce cuando un atributo depende de otro atributo que no es clave primaria. Ejemplo: 

DNI→Departamento 

Departamento→Ubicación 

Como resultado, **DNI → Ubicación** es una dependencia transitiva. 

# **4.1 Principales formas normales** 

Las **formas normales** son conjuntos de reglas que mejoran la estructura de las bases de datos. Se aplican en orden, desde la **Primera Forma Normal (1FN)** hasta la **Forma Normal de Boyce-Codd (BCNF)** , y cada una corrige ciertos problemas estructurales. 

- **1FN (Primera Forma Normal):** Eliminación de valores repetidos en columnas. Los valores de cada columna deben de ser atómicos. 

- **2FN (Segunda Forma Normal):** Dependencia total de la clave primaria. Cada atributo depende de la clave. Elimina dependencias parciales de la clave primaria. 

- 

   - **3FN (Tercera Forma Normal):** Eliminación de dependencias transitivas. 

- **BCNF (Forma Normal de Boyce-Codd):** Mejora la 3FN eliminando anomalías más complejas. 

# **4.1.1. Primera Forma Normal (1FN)** 

Una relación está en **1FN** si: 

- **Todos los atributos contienen valores atómicos (no repetidos ni conjuntos de valores).** 

- 

- 

- **Cada columna tiene un único tipo de dato.** 

- **Cada fila es única y tiene una clave primaria.** 

**Ejemplo de tabla NO en 1FN (atributos multivaluados):** 

# **ID_Cliente Nombre Teléfono** 

|**1**|Juan|654321, 987654|
|---|---|---|
|**2**|María|678912|



**Solución en 1FN (separar valores en filas):** 

# **ID_Cliente Nombre Teléfono** 

|**1**|Juan|654321|
|---|---|---|
|**1**|Juan|987654|
|**2**|María|678912|



# **4.1.2. Segunda Forma Normal (2FN)** 

Una relación está en **2FN** si: 

1. **Está en 1FN.** 

2. **Todos los atributos no clave dependen completamente de la clave primaria, no solo de una parte de ella.** 

**Ejemplo de tabla NO en 2FN (dependencia parcial de clave compuesta):** 

# **ID_Pedido ID_Producto Nombre_Producto Cantidad** 

|**1**|A1|Teclado|2|
|---|---|---|---|
|**1**|B2|Ratón|1|



- **Clave primaria:** _(ID_Pedido, ID_Producto)_ 

- **Problema: Nombre_Producto** depende solo de **ID_Producto** , no de la clave completa. 

**Solución en 2FN (crear una tabla para productos): Tabla Pedidos:** 

# **ID_Pedido ID_Producto Cantidad** 

|**1**|A1|2|
|---|---|---|
|**1**|B2|1|



# **Tabla Productos:** 

# **ID_Producto Nombre_Producto** 

|**A1**|Teclado|
|---|---|
|**B2**|Ratón|



# **4.1.3. Tercera Forma Normal (3FN)** 

Una relación está en **3FN** si: 

1. **Está en 2FN.** 

2. **No existen dependencias transitivas (los atributos dependen directamente de la clave primaria, no de otros atributos no clave).** 

**Ejemplo de tabla NO en 3FN (dependencia transitiva):** 

**ID_Empleado Nombre ID_Departamento Nombre_Departamento** 

|**1**|Juan|D01|Ventas|
|---|---|---|---|
|**2**|María|D02|Contabilidad|



- **Clave primaria: ID_Empleado** 

- **Problema: Nombre_Departamento** depende de **ID_Departamento** , que no es clave primaria. 

**Solución en 3FN (crear una tabla de departamentos): Tabla Empleados:** 

# **ID_Empleado Nombre ID_Departamento** 

|**1**|Juan|D01|
|---|---|---|
|**2**|María|D02|



# **Tabla Departamentos:** 

**ID_Departamento Nombre_Departamento** 

|**D01**|Ventas|
|---|---|
|**D02**|Contabilidad|



# **4.1.4. Forma Normal de Boyce-Codd (BCNF)** 

La **BCNF** es una versión más estricta de la **3FN** . Se cumple si: 

1. **Está en 3FN.** 

2. **Cada determinante es una clave candidata (no hay dependencias funcionales de atributos que no sean claves primarias).** 

**Ejemplo de tabla NO en BCNF (dependencia funcional en clave secundaria):** 

# **ID_Profesor ID_Curso Aula** 

|**P1**|C1|101|
|---|---|---|
|**P2**|C2|102|



- **Clave primaria:** _(ID_Profesor, ID_Curso)_ 

- **Problema: Aula** depende de **ID_Curso** , pero **ID_Curso** no es clave primaria. 

**Solución en BCNF (crear una tabla para cursos y aulas): Tabla Profesores-Cursos:** 

# **ID_Profesor ID_Curso** 

|**P1**|C1|
|---|---|
|**P2**|C2|



**Tabla Cursos:** 

# **ID_Curso Aula** 

|**C1**|101|
|---|---|
|**C2**|102|



# **4.1.5. Cuarta Forma Normal (4FN)** 

Una relación está en 4FN si está en FNBC y no contiene **dependencias multivaluadas** no triviales (salvo aquellas cuyo determinante es superclave). 

Existe una dependencia multivaluada X →→ Y cuando a cada valor de X le corresponde un conjunto de valores de Y, independiente del resto de atributos. Ejemplo: en PROFESOR(Profesor, Asignatura, Idioma), si un profesor imparte varias asignaturas y habla varios idiomas de forma independiente, hay que repetir todas las combinaciones. Solución: descomponer en PROFESOR_ASIGNATURA(Profesor, Asignatura) y PROFESOR_IDIOMA(Profesor, Idioma). 

# **4.1.6. Quinta Forma Normal (5FN o FNPJ)** 

También llamada Forma Normal de Proyección-Unión (FNPJ). Una relación está en 5FN si está en 4FN y toda **dependencia de unión (join)** está implicada por sus claves candidatas; es decir, no puede descomponerse en tablas más pequeñas sin pérdida de 

información salvo a través de sus claves. Afecta a relaciones ternarias o superiores con restricciones cíclicas. 

# **4.1.7. Jerarquía de las formas normales** 

Las formas normales son acumulativas: cada una exige cumplir la anterior. El orden completo es: 

**1FN → 2FN → 3FN → FNBC → 4FN → 5FN** (existen otras teóricas, como la Forma Normal Dominio-Clave (FNDC) y la 6FN). 

Por tanto, la **Forma Normal de Boyce-Codd (FNBC)** se sitúa **entre la 3FN y la 4FN** : toda relación en FNBC está en 3FN, pero no toda relación en 3FN está en FNBC. Las tres primeras y la FNBC se basan en dependencias funcionales; la 4FN en dependencias multivaluadas; y la 5FN en dependencias de unión. 

# **4.2. Importancia de la Normalización** 

La normalización **reduce la redundancia** y evita **anomalías de actualización** , pero **puede afectar el rendimiento** al aumentar el número de tablas y relaciones. En algunos casos, se puede aplicar **desnormalización** para mejorar la velocidad de consulta. 

**Ventajas de la Normalización** 

Elimina la redundancia. 

Mejora la integridad de los datos. 

Facilita la actualización de registros. 

Minimiza las anomalías en inserciones, eliminaciones y modificaciones. 

**Desventajas de la Normalización** 

Puede generar muchas tablas, complicando consultas. 

Algunas consultas pueden volverse más lentas por la necesidad de unir varias tablas. 

# **5. Manipulación de Datos: Álgebra y Cálculo Relacional** 

# **5.1. Álgebra Relacional** 

El **álgebra relacional** es un lenguaje formal basado en operaciones matemáticas que permite manipular y consultar datos en una base de datos relacional. Se trata de un **lenguaje procedimental** , ya que las operaciones se aplican a una o varias relaciones para obtener otra relación como resultado. 

**Características del Álgebra Relacional** 

**Opera sobre conjuntos de datos (tablas).** 

**El resultado de una operación es otra relación. Permite combinar y filtrar datos mediante operaciones matemáticas. Facilita la optimización de consultas en bases de datos.** 

Las operaciones del álgebra relacional se dividen en: 

1. **Operaciones fundamentales o básicas** (selección, proyección, unión, diferencia y producto cartesiano). 

2. **Operaciones derivadas o adicionales** (intersección, división y unión externa). 

# **5.2. Descripción de Operaciones Básicas** 

# **5.2.1. Selección (σ) (también denominada restricción)** 

La selección permite **filtrar filas** de una relación basándose en una condición. 

**Notación:** σcondicion(R)  (R WHERE condición) 

Donde: 

- R es la relación. 

- **Condición** es una expresión lógica aplicada a los atributos. 

**Ejemplo:** Si tenemos la relación **Empleados** : 

|**ID**|**Nombre**|**Departamento**|**Salario**|
|---|---|---|---|
|**1**|Juan|Ventas|2000|
|**2**|María|Contabilidad|2500|
|**3**|Pedro|Ventas|2200|



Consulta: Obtener empleados del departamento "Ventas". 

- σDepartamento=′Ventas′(Empleados) 

Resultado: 

|**ID**|**Nombre**|**Departamento**|**Salario**|
|---|---|---|---|
|**1**|Juan|Ventas|2000|
|**3**|Pedro|Ventas|2200|



# **5.2.2. Proyección (π)** 

La proyección permite **seleccionar columnas** de una relación, eliminando atributos innecesarios. 

**Notación:** πatributos(R)  (R[ai, ..., ak]) 

**Ejemplo:** Consulta: Obtener solo los nombres y salarios de los empleados. 

πNombre, Salario(Empleados) 

Resultado: 

|**Nombre**|**Salario**|
|---|---|
|**Juan**|2000|
|**María**|2500|
|**Pedro**|2200|



# **5.2.3. Unión (** ∪ **)** 

La unión combina **dos relaciones compatibles** , es decir, que tienen los mismos atributos. 

**Notación:** R∪S (R UNION S) 

**Ejemplo:** Dadas las relaciones **Empleados_España** y **Empleados_México** con la misma estructura, la unión obtiene una lista combinada de empleados. 

# **5.2.4. Diferencia (−)** 

La diferencia devuelve las tuplas que están en una relación pero **no en otra** . 

**Notación:** R−S  (R MINUS S) 

**Ejemplo:** Si **Empleados** contiene todos los empleados y **Empleados_Ventas** solo los del departamento de ventas, la diferencia obtiene los empleados que **no** trabajan en ventas. 

# **5.2.5. Producto Cartesiano (×)** 

El producto cartesiano combina **todas las tuplas** de dos relaciones. 

**Notación:** R×S (R TIMES S) 

**Ejemplo:** Si **Clientes** tiene 5 registros y **Pedidos** tiene 10 registros, el resultado del producto cartesiano tendrá **50 filas** (5 × 10). 

# **5.3. Descripción de Operaciones Adicionales** 

# **5.3.1. Intersección (∩)** 

La intersección devuelve las tuplas **comunes** entre dos relaciones. 

**Notación:** R∩S (R INTERSECT S) 

**Ejemplo:** Si **Clientes_A** y **Clientes_B** contienen clientes de diferentes países, la intersección muestra los clientes comunes. 

# **5.3.2. División (÷)** 

La división obtiene las tuplas de una relación que están relacionadas con **todas** las tuplas de otra. 

**Notación:** R÷S (R DIVIDEDBY S) 

**Ejemplo:** Si una tabla **AlumnosCursos** indica qué cursos ha tomado cada alumno y otra tabla **CursosObligatorios** enumera los cursos requeridos para graduarse, la división devuelve los alumnos que han completado **todos** los cursos obligatorios. 

# **5.3.3. Unión (** ⋈ **)** 

La unión (R JOIN S) obtiene una relación cuyas tuplas están formadas por todos los pares de tuplas de las dos relaciones cuyos atributos contienen los mismos valores. Es un producto cartesiano y una restricción de igualdad sobre los atributos comunes. 

**Ejemplo:** Si tenemos una tabla de **Clientes** y otra de **Pedidos** , una **unión izquierda** devolvería todos los clientes, que tengan pedidos. 

# **5.3.4. Unión Externa (** ⟖ **,** ⟗ **,** ⟕ **)** 

La unión externa es una variación de la **unión normal** , pero incluye también las filas que no tienen correspondencia. 

- **Unión externa izquierda (** ⟕ **) (LEFT OUTER JOIN):** Devuelve todas las filas de la **izquierda** , aunque no tengan coincidencia en la derecha. 

- **Unión externa derecha (** ⟖ **) (RIGHT OUTER JOIN):** Devuelve todas las filas de la **derecha** , aunque no tengan coincidencia en la izquierda. 

- **Unión externa completa (** ⟗ **) (FULL OUTER JOIN):** Devuelve todas las filas de ambas tablas, incluyendo valores **NULL** donde no haya coincidencia. 

**Ejemplo:** Si tenemos una tabla de **Clientes** y otra de **Pedidos** , una **unión externa izquierda** devolvería todos los clientes, incluso aquellos sin pedidos. 

# **5.4. Cálculo Relacional de Tuplas (TRC)** 

Utiliza expresiones lógicas para definir consultas mediante condiciones. 

- **Basado en lógica de primer orden** 

- **Expresiones con variables y condiciones** para recuperar datos 

El **Cálculo Relacional de Tuplas** selecciona **tuplas** de una relación según una condición lógica. 

**Notación General:** {t ∣ Condición(t)} 

Donde: 

- t representa una **tupla** en la relación. 

- La **Condición** es una expresión lógica que debe cumplirse. 

**Ejemplo:** Dada una relación **Empleados(ID, Nombre, Salario, Departamento)** , si queremos encontrar los empleados con un salario mayor a 2000: 

{t∣t∈Empleados∧t.Salario>2000} 

Esto selecciona todas las **tuplas** donde el salario es mayor a 2000. 

**Operadores comunes en TRC:** 

- ∧ **(AND):** Conjunción de condiciones. 

- ∨ **(OR):** Disyunción de condiciones. 

- **¬ (NOT):** Negación de condiciones. 

- ∃ **(EXISTS):** Existen al menos una tupla que cumpla la condición. 

- ∀ **(FOR ALL):** Se debe cumplir la condición para todas las tuplas. 

**Ejemplo con cuantificadores:** 

Si queremos obtener los empleados que trabajan en **Ventas** , podemos escribir: 

{t ∣ t ∈ Empleados ∧ t.Departamento = ′Ventas′} 

# **5.5. Cálculo Relacional de Dominios (DRC)** 

El **Cálculo Relacional de Dominios** se basa en **valores individuales** en lugar de tuplas completas. 

**Notación General:** {(d1, d2, ..., dn) ∣ Condición(d1, d2 , ..., dn)} 

Donde: 

- d1, d2, ..., dnd_1, d_2, ..., d_nd1,  d2,...,dn representan **valores de atributos específicos** . 

- La **Condición** es una expresión lógica basada en valores de dominio. 

**Ejemplo:** Dada la relación **Empleados(ID, Nombre, Salario, Departamento)** , si queremos encontrar los nombres de los empleados que ganan más de 2000: 

{d ∣ ∃i, s, d(Empleados(i,d,s,) ∧ s>2000)} 

Esto significa: 

- Existen valores **i, s y d** en la relación **Empleados** donde **s (Salario) > 2000** . 

- Se devuelve el dominio **d (Nombre del empleado)** . 

# **Comparación TRC vs. DRC:** 

|**Característica**|**Cálculo Relacional de**<br>**Tuplas (TRC)**|**Cálculo Relacional de**<br>**Dominios (DRC)**|
|---|---|---|
|**Selección de datos**|Tuplas completas|Valores individuales|
|**Basado en**|Variables de tupla|Variables de dominio|
|**Expresión de**<br>**consultas**|Similar a SQL|Más compacto pero complejo|



# **5.6. Relación con SQL** 

El cálculo relacional es la base teórica del lenguaje **SQL** , que combina aspectos tanto del álgebra relacional como del cálculo relacional. 

# **Ejemplo en SQL equivalente a TRC y DRC:** 

SELECT Nombre FROM Empleados WHERE Salario > 2000; 

Este comando obtiene los nombres de los empleados con salario superior a 2000, equivalente a la consulta en cálculo relacional. 

# **6. Lenguaje SQL (Structured Query Language)** 

SQL es el estándar para la manipulación de bases de datos relacionales. 

SQL es un lenguaje **declarativo** (no procedimental): se indica QUÉ datos se quieren obtener, no CÓMO obtenerlos; el optimizador del SGBD decide el plan de ejecución. Por esta razón se clasifica como un **lenguaje de cuarta generación (4GL)** . Fue desarrollado por IBM en los años 70 (SEQUEL, para System R) y está normalizado por ANSI (1986) e ISO (SQL-87, SQL-92, SQL:1999, SQL:2003, SQL:2011, SQL:2016, SQL:2023). 

|**Generación**|**Características**|**Ejemplos**|
|---|---|---|
|**1GL**|Código máquina (binario).|Instrucciones binarias<br>del procesador|
|**2GL**|Lenguajes ensambladores (mnemónicos).|Ensamblador|
|**3GL**|Lenguajes de alto nivel procedimentales.|C, COBOL, Pascal, Java|
|**4GL**|Lenguajes declarativos, orientados a un<br>dominio (datos, informes), próximos al<br>lenguaje natural.|SQL, generadores de<br>informes|
|**5GL**|Basados en lógica y restricciones, orientados<br>a la inteligencia artificial.|Prolog, Mercury|



Los SGBD añaden extensiones procedimentales a SQL: **PL/SQL** (Oracle), **Transact-SQL o T-SQL** (SQL Server) y **PL/pgSQL** (PostgreSQL). 

# **6.1 Principales comandos SQL** 

- **DDL (Data Definition Language)** : CREATE TABLE, ALTER TABLE, DROP TABLE. 

- **DML (Data Manipulation Language)** : SELECT, INSERT, UPDATE, DELETE. 

- **DCL (Data Control Language)** : GRANT, REVOKE. 

- **TCL (Transaction Control Language)** : COMMIT, ROLLBACK. 

# **6.1.1. Lenguaje de Definición de Datos (DDL)** 

El **Lenguaje de Definición de Datos (DDL, Data Definition Language)** se utiliza para **crear, modificar y eliminar** la estructura de las bases de datos. Las sentencias DDL no manipulan datos directamente, sino que afectan a los esquemas y objetos de la base de datos. 

# • **Principales sentencias DDL** 

|**Sentencia**|**Descripción**|
|---|---|
|**CREATE TABLE**|Crea una nueva tabla en la base de datos.|
|**ALTER TABLE**|Modifica la estructura de una tabla existente.|
|**DROP TABLE**|Elimina una tabla y todos sus datos.|
|**CREATE INDEX**|Crea un índice en una o más columnas de una tabla.|
|**CREATE VIEW**|Define una vista basada en una consulta.|



   - **Ejemplo de uso de DDL** 

**1. Creación de una tabla (CREATE TABLE)** 

CREATE TABLE Empleados ( ID INT PRIMARY KEY, Nombre VARCHAR(50) NOT NULL, Salario DECIMAL(10,2), Departamento VARCHAR(30) ); 

- Esta sentencia define la estructura de la tabla **Empleados** con cuatro columnas. 

**2. Modificación de una tabla (ALTER TABLE)** 

ALTER TABLE Empleados ADD Edad INT; 

- Añade la columna **Edad** a la tabla **Empleados** . 

**3. Eliminación de una tabla (DROP TABLE)** 

DROP TABLE Empleados; 

- Borra la tabla **Empleados** y todos sus datos. 

# **6.1.2. Lenguaje de Manipulación de Datos (DML)** 

El **Lenguaje de Manipulación de Datos (DML, Data Manipulation Language)** permite a los usuarios **consultar, insertar, actualizar y eliminar datos** dentro de las tablas de la base de datos. 

# • **Principales sentencias DML** 

|**Sentencia**|**Descripción**|
|---|---|
|**SELECT**|Recupera datos de una o más tablas.|
|**INSERT**|Inserta nuevas filas en una tabla.|
|**UPDATE**|Modifica datos existentes en una tabla.|
|**DELETE**|Elimina filas de una tabla.|



   - **Ejemplo de uso de DML** 

**1. Consulta de datos (SELECT)** 

SELECT Nombre, Salario FROM Empleados WHERE Departamento = 'Ventas'; 

- Obtiene los nombres y salarios de los empleados del departamento de ventas. 

# **2. Inserción de datos (INSERT)** 

INSERT INTO Empleados (ID, Nombre, Salario, Departamento) VALUES (1, 'Juan Pérez', 2500, 'Ventas'); 

- Inserta un nuevo empleado en la tabla. 

# **3. Actualización de datos (UPDATE)** 

UPDATE Empleados SET Salario = 3000 WHERE ID = 1; 

- Modifica el salario del empleado con ID 1. 

# **4. Eliminación de datos (DELETE)** 

DELETE FROM Empleados WHERE ID = 1; 

- Elimina el empleado con ID 1 de la tabla. 

# **6.1.3. Lenguaje de Control de Datos (DCL)** 

El **Lenguaje de Control de Datos (DCL, Data Control Language)** gestiona los 

permisos y la seguridad de la base de datos. Permite definir qué usuarios pueden acceder a qué datos y con qué permisos. 

# • **Principales sentencias DCL** 

|**Sentencia**|**Descripción**|
|---|---|
|**GRANT**|Concede permisos a un usuario.|
|**REVOKE**|Revoca permisos previamente concedidos.|



# • **Ejemplo de uso de DCL** 

# **1. Conceder permisos (GRANT)** 

GRANT SELECT, INSERT ON Empleados TO usuario1; 

- Otorga permisos para consultar e insertar datos en la tabla **Empleados** al usuario **usuario1** . 

**2. Revocar permisos (REVOKE)** 

REVOKE INSERT ON Empleados FROM usuario1; 

- Revoca el permiso de inserción en la tabla **Empleados** al usuario **usuario1** . 

# **6.1.4. Lenguaje de Transacciones (TCL)** 

El **Lenguaje de Control de Transacciones (TCL, Transaction Control Language)** se encarga de gestionar la integridad de los datos en operaciones que afectan múltiples registros. 

# • **Principales sentencias TCL** 

|**Sentencia**|**Descripción**|
|---|---|
|**COMMIT**|Guarda de forma permanente los cambios realizados en la base<br>de datos.|
|**ROLLBACK**|Revierte los cambios no confirmados.|
|**SAVEPOINT**|Crea un punto de guardado dentro de una transacción para hacer<br>un rollback parcial.|



# • **Ejemplo de uso de TCL** 

**1. Confirmación de cambios (COMMIT)** 

BEGIN TRANSACTION; UPDATE Empleados SET Salario = 3200 WHERE ID = 1; COMMIT; 

- Guarda de forma permanente la actualización del salario. 

**2. Deshacer cambios (ROLLBACK)** 

BEGIN TRANSACTION; UPDATE Empleados SET Salario = 3200 WHERE ID = 1; ROLLBACK; 

- Revierte el cambio y deja el salario como estaba antes. 

# **3. Crear un punto de guardado (SAVEPOINT)** 

SAVEPOINT punto1; UPDATE Empleados SET Salario = 3500 WHERE ID = 2; ROLLBACK TO punto1; 

- Crea un punto de restauración y permite revertir los cambios hasta ese punto sin afectar otras modificaciones. 

# **6.2. Sentencia TRUNCATE** 

TRUNCATE TABLE elimina **todas las filas** de una tabla conservando su estructura (columnas, índices, restricciones y permisos). Aunque su efecto se parece a un DELETE sin WHERE, es una sentencia **DDL** : 

- Es **mucho más rápida que DELETE** , porque no borra fila a fila ni genera información de deshacer (undo) por cada fila; libera los bloques de la tabla y reinicia la marca de agua alta (High Water Mark). 

- En Oracle realiza un COMMIT implícito, por lo que **no puede deshacerse con ROLLBACK** . 

- No admite cláusula WHERE y no dispara los triggers de DELETE. 

- **Con claves foráneas activas:** si la tabla está referenciada por una clave foránea habilitada, TRUNCATE **lanza un error** (en Oracle, ORA-02266), aunque la tabla hija no tenga filas. Hay que deshabilitar la restricción antes. Desde Oracle 12c existe TRUNCATE TABLE ... CASCADE, que solo funciona si las claves foráneas están definidas con ON DELETE CASCADE. En SQL Server tampoco se puede truncar una tabla referenciada por una FK, y en PostgreSQL da error salvo que se use TRUNCATE ... CASCADE. 

||**DELETE**|**TRUNCATE**|**DROP**|
|---|---|---|---|
|**Tipo**|DML|DDL|DDL|
|**Qué elimina**|Filas (todas o las del<br>WHERE)|Todas las filas|La tabla completa<br>(estructura y datos)|
|**WHERE**|Sí|No|No|
|**ROLLBACK**|Sí|No (COMMIT<br>implícito en Oracle)|No (salvo papelera<br>FLASHBACK en<br>Oracle)|
|**Velocidad**|Lenta (fila a fila)|Muy rápida|Muy rápida|
|**Triggers**|Dispara triggers<br>DELETE|No|No|



```
TRUNCATE TABLE Empleados;
```

# **6.3. Subconsultas correlacionadas en UPDATE** 

Una **subconsulta correlacionada** es aquella que hace referencia a columnas de la consulta externa, por lo que se evalúa una vez por cada fila de la tabla que se actualiza. Es la forma estándar de actualizar una tabla con valores de otra. Para referenciar la tabla externa dentro de la subconsulta se suelen usar **alias** de tabla. 

Sintaxis estándar / Oracle (alias en la cláusula UPDATE): 

```
UPDATE PACIENTE_ESPECIALIZADA A
   SET resultado_prueba_e = (SELECT B.resultado_prueba_p
                               FROM PACIENTE_PRIMARIA B
                              WHERE A.nuhsa = B.nuhsa
                                AND A.dni   = B.dni
                                AND B.fecha_prueba <= SYSDATE);
```

Claves para identificar la sentencia correcta: 

- Las condiciones de unión entre ambas tablas deben ir **dentro** de la subconsulta; si van en el WHERE externo, la tabla de la subconsulta no es visible y la sentencia es errónea. 

- La sintaxis UPDATE ... SET sin indicar la tabla a actualizar (UPDATE columna = ...) es incorrecta. 

- Si la subconsulta no encuentra fila, la columna se actualiza a NULL; para evitarlo se añade WHERE EXISTS (subconsulta) en el UPDATE externo. Si devuelve más de una fila, se produce un error. 

- La función de fecha actual varía: SYSDATE (Oracle), GETDATE() (SQL Server), NOW() / CURRENT_DATE (MySQL, PostgreSQL). 

En SQL Server (T-SQL) también existe la sintaxis propietaria con FROM y JOIN, donde el alias se declara en la cláusula FROM: 

```
UPDATE A
   SET A.resultado_prueba_e = B.resultado_prueba_p
  FROM PACIENTE_ESPECIALIZADA A
  JOIN PACIENTE_PRIMARIA B ON A.nuhsa = B.nuhsa AND A.dni = B.dni
 WHERE B.fecha_prueba <= GETDATE();
```

# **6.4. Funciones y sentencias SQL avanzadas** 

- **LISTAGG** (Oracle 11gR2+): función de agregación que concatena en una sola cadena los valores de varias filas, con el separador indicado. Equivalentes: STRING_AGG (SQL Server 2017+, PostgreSQL) y GROUP_CONCAT (MySQL). 

```
SELECT LISTAGG(nombre, ', ') WITHIN GROUP (ORDER BY nombre) AS pacientes
  FROM Pacientes;
-- Resultado: Ana, Juan, Luis, María
```

- **PIVOT:** transforma filas en columnas (p. ej., una columna por cada mes a partir de los valores de un campo mes). 

- **UNPIVOT:** operación inversa; transforma columnas en filas. 

- **MERGE:** combina en una sola sentencia INSERT, UPDATE (y DELETE) sobre una tabla destino según exista o no coincidencia con un origen («upsert»). 

```
MERGE INTO Destino D USING Origen O ON (D.id = O.id)
 WHEN MATCHED THEN UPDATE SET D.valor = O.valor
 WHEN NOT MATCHED THEN INSERT (id, valor) VALUES (O.id, O.valor);
```

# **6.5. Procedimientos almacenados** 

Un **procedimiento almacenado** es un programa (conjunto de sentencias SQL y de control de flujo) que se guarda compilado **en la propia base de datos** y se ejecuta en el servidor. Ventajas: mejor rendimiento (el plan de ejecución se compila y se reutiliza), menos tráfico de red (se envía solo la llamada), seguridad (se concede permiso EXECUTE sin dar acceso a las tablas), reutilización y centralización de la lógica de negocio. En Oracle se escriben en PL/SQL; en SQL Server en T-SQL; en PostgreSQL en PL/pgSQL. 

# **7. Normas y Estándares para la Interoperabilidad entre SGBD** 

La **interoperabilidad en bases de datos** se refiere a la capacidad de diferentes sistemas de gestión de bases de datos (SGBD) para **comunicarse y compartir información de manera eficiente** , incluso si están desarrollados por distintos fabricantes o utilizan arquitecturas diferentes. 

En el entorno actual, donde los sistemas informáticos suelen estar distribuidos y utilizar múltiples tecnologías, la interoperabilidad se vuelve esencial para permitir el acceso y la manipulación de datos desde diversas aplicaciones. 

Para lograr la interoperabilidad, se han desarrollado **estándares (SQL ANSI/ISO** ) **y tecnologías** que permiten la conexión y el intercambio de información entre distintos SGBD, como **ODBC (Open Database Connectivity)** y **JDBC (Java Database Connectivity)** . 

# **7.1. Estándares de Conectividad** 

El principal desafío en la interoperabilidad es la diversidad de sistemas y protocolos utilizados en diferentes bases de datos. Para abordar este problema, se han desarrollado **estándares de conectividad** que permiten a las aplicaciones acceder a diversas bases de datos de manera uniforme. 

Las **APIs (Interfaces de Programación de Aplicaciones)** proporcionan funciones estándar para interactuar con bases de datos sin depender de un SGBD específico. 

Las tecnologías más utilizadas para la interoperabilidad en bases de datos son: 

- **ODBC (Open Database Connectivity)** 

- **JDBC (Java Database Connectivity)** 

Estos estándares permiten que una aplicación pueda comunicarse con múltiples bases de datos utilizando un **lenguaje común** , sin importar qué SGBD se esté utilizando. 

# **7.2. ODBC (Open Database Connectivity)** 

ODBC es un estándar de acceso a bases de datos desarrollado por **Microsoft** que permite que cualquier aplicación acceda a cualquier base de datos, independientemente del sistema de gestión de bases de datos utilizado. 

# **Características de ODBC** 

**Independencia del SGBD:** La aplicación no necesita conocer detalles específicos del SGBD. 

**Uso de controladores (drivers):** Cada SGBD necesita un driver ODBC específico que actúa como intermediario. 

**Interfaz de alto nivel:** Permite ejecutar consultas SQL estándar. 

**Compatibilidad multiplataforma:** Disponible para **Windows, Unix, OS/2 y MacOS** . 

# **Arquitectura de ODBC** 

ODBC tiene **cuatro capas** principales: 

1. **Aplicación:** Realiza las consultas y procesa los resultados. 

2. **Driver Manager:** Administra los controladores ODBC y enruta las peticiones a los drivers adecuados. 

3. **Driver ODBC:** Traduce las llamadas de la aplicación a comandos específicos del SGBD. 

4. **Fuente de Datos:** Contiene los datos y su SGBD correspondiente. 

**Ejemplo de conexión ODBC en C:** 

SQLAllocHandle(SQL_HANDLE_ENV, SQL_NULL_HANDLE, &env); SQLSetEnvAttr(env, SQL_ATTR_ODBC_VERSION, (SQLPOINTER) SQL_OV_ODBC3, 0); SQLAllocHandle(SQL_HANDLE_DBC, env, &dbc); SQLConnect(dbc, (SQLCHAR*)"MiBaseDeDatos", SQL_NTS, (SQLCHAR*)"usuario", SQL_NTS, (SQLCHAR*)"contraseña", SQL_NTS); 

# **Ventajas de ODBC** 

Permite el acceso a múltiples SGBD desde una única aplicación. 

Compatible con SQL estándar. 

Reduce el desarrollo específico para cada SGBD. 

# **Desventajas de ODBC** 

El rendimiento puede verse afectado por la capa de abstracción. Requiere instalación y configuración de controladores en el sistema operativo. 

# **7.3. JDBC (Java Database Connectivity)** 

JDBC es una API de **Java** desarrollada por **Sun Microsystems** que permite a los programas Java ejecutar consultas SQL en bases de datos. 

# **Características de JDBC** 

Diseñado específicamente para aplicaciones Java. 

Permite la ejecución de sentencias SQL. 

Usa controladores para conectarse a diferentes SGBD. 

Compatible con múltiples sistemas operativos y bases de datos. 

# **Arquitectura de JDBC** 

JDBC define cuatro tipos de controladores para acceder a bases de datos: 

1. **Driver JDBC-ODBC Bridge:** Usa ODBC para conectarse a bases de datos (menos eficiente). 

2. **Driver Nativo (Native API):** Convierte llamadas JDBC en llamadas a la API nativa del SGBD. 

3. **Driver Intermedio (Network Protocol):** Traduce las llamadas JDBC en protocolos independientes del SGBD. 

4. **Driver Puro Java:** Implementado completamente en Java, se conecta directamente a la base de datos. 

**Ejemplo de conexión JDBC en Java:** 

import java.sql.*; public class ConexionBD { public static void main(String[] args) { try { Connection con = DriverManager.getConnection("jdbc:mysql://localhost:3306/miBase", "usuario", "contraseña"); Statement stmt = con.createStatement(); ResultSet rs = stmt.executeQuery("SELECT * FROM Empleados"); while (rs.next()) { System.out.println(rs.getString("Nombre")); } con.close(); } catch (Exception e) { e.printStackTrace(); } } } 

# **Ventajas de JDBC** 

Totalmente integrado con Java. Independiente de la plataforma. Soporte para transacciones y seguridad avanzada. 

# **Desventajas de JDBC** 

Requiere un driver compatible con el SGBD utilizado. Puede ser más lento que una conexión nativa. 

# **7.4. Comparación entre ODBC y JDBC** 

|**Característica**|**ODBC**|**JDBC**|
|---|---|---|
|**Lenguaje**|Compatible con múltiples lenguajes<br>(C, C++, Python, etc.)|Solo para Java|
|**Plataforma**|Dependiente del sistema operativo|Independiente (Java)|
|**Dependencia de**<br>**drivers**|Requiere drivers ODBC para cada<br>SGBD|Requiere drivers JDBC<br>específicos|
|**Rendimiento**|Mayor sobre Windows|Mejor optimización en<br>entornos Java|
|**Uso**|Aplicaciones de escritorio y<br>servidores|Aplicaciones web y<br>móviles en Java|



# **7.5. Importancia de la Interoperabilidad** 

La interoperabilidad en bases de datos es clave en entornos donde **varios sistemas deben interactuar** . Algunos escenarios comunes incluyen: 

- **Aplicaciones empresariales:** Donde diferentes departamentos utilizan SGBD distintos. 

- **Sistemas distribuidos:** Bases de datos en diferentes ubicaciones geográficas. 

- **Migración de datos:** Transferencia de información entre plataformas heterogéneas. 

- **Integración con aplicaciones de terceros:** Software externo que necesita acceder a la base de datos. 

Los estándares como **ODBC y JDBC** facilitan la integración de bases de datos con diversas aplicaciones, reduciendo la complejidad en el desarrollo y mejorando la eficiencia en el acceso a los datos. 

# **8. Sistemas de Gestión de Bases de Datos (SGBD)** 

Un **Sistema de Gestión de Bases de Datos (SGBD)** es un software que permite a los usuarios y aplicaciones **crear, administrar y manipular** bases de datos de manera eficiente y segura. Su función principal es facilitar el almacenamiento, recuperación y actualización de los datos de una manera estructurada, asegurando la integridad y la consistencia de la información. 

# **8.1. Características de los SGBD** 

Los SGBD modernos tienen varias características esenciales: 

**Independencia de datos:** Separa los datos de las aplicaciones que los utilizan. **Acceso concurrente:** Permite que múltiples usuarios accedan a la base de datos simultáneamente. 

**Integridad de datos:** Mantiene reglas y restricciones para evitar inconsistencias. **Seguridad:** Controla el acceso a los datos mediante autenticación y permisos. **Lenguaje de consulta estructurado (SQL):** Proporciona un medio estandarizado para interactuar con los datos. 

**Gestión de transacciones:** Asegura la consistencia y recuperación de datos en caso de fallos. 

Los SGBD son ampliamente utilizados en empresas, gobiernos y organizaciones para gestionar grandes volúmenes de información en distintos ámbitos como finanzas, salud, educación, comercio electrónico, entre otros.

# **8.3.1.1. Arquitectura de Oracle: instancia y base de datos** 

En Oracle se distingue entre **instancia** (estructuras de memoria + procesos) y **base de datos** (ficheros físicos en disco). 

- **SGA (System Global Area):** memoria compartida de la instancia. Incluye la database buffer cache (bloques de datos), el shared pool (library cache con SQL y PL/SQL analizado, y dictionary cache), el redo log buffer, el large pool y el java pool. Es memoria volátil: su contenido se pierde en una parada abrupta. 

- **PGA (Program Global Area):** memoria privada de cada proceso servidor. 

- **Procesos en segundo plano:** DBWn (escribe bloques modificados en los datafiles), LGWR (escribe el redo log buffer en los redo log en línea; lo hace en cada COMMIT), CKPT (checkpoints), SMON (recuperación de la instancia), PMON (limpieza de procesos caídos), ARCn (archivado de redo logs), MMON (estadísticas AWR), RECO (transacciones distribuidas). 

# **8.3.1.2. Tipos de ficheros de una base de datos Oracle** 

Los ficheros que forman la base de datos son tres: 

- **Ficheros de datos (datafiles):** contienen los datos de tablas, índices, etc. Se agrupan lógicamente en tablespaces. 

- **Ficheros de control (control files):** almacenan la estructura física de la BD (nombre, ubicación de datafiles y redo logs, SCN, checkpoints). Se multiplexan por seguridad. 

- **Ficheros de redo log (online redo logs):** registran todos los cambios realizados en la BD para poder recuperarla. Se organizan en grupos y miembros, y se usan de forma circular. 

Además, la instancia utiliza otros ficheros: fichero de parámetros (PFILE init.ora o SPFILE), fichero de contraseñas, **redo logs archivados** (en modo ARCHIVELOG), y ficheros de diagnóstico (alert.log y trazas). El **fichero de backup NO es un tipo de fichero del SGBD** : las copias de seguridad son ficheros externos generados por herramientas como RMAN o Data Pump. 

**Estructura lógica:** Base de datos → tablespaces (SYSTEM, SYSAUX, UNDO, TEMP, USERS…) → segmentos → extensiones → bloques de datos. 

# **8.3.1.3. Esquema y usuario** 

En Oracle, un **esquema** es el conjunto de objetos (tablas, vistas, índices, secuencias, procedimientos…) que pertenecen a una cuenta de usuario. Existe una correspondencia 1:1: al crear un usuario se crea su esquema, con el mismo nombre. Por eso, el concepto de esquema se asemeja más al de **usuario** (no a un tablespace, a los datafiles ni a los procesos). 

# **8.3.1.4. Creación de usuarios, perfiles y roles** 

```
CREATE USER ROSA IDENTIFIED BY Rosa22
  DEFAULT TABLESPACE users
  TEMPORARY TABLESPACE temp
  QUOTA 500M ON users
  PROFILE default;
```

- En CREATE USER solo son obligatorios el nombre y la cláusula IDENTIFIED. **DEFAULT TABLESPACE, TEMPORARY TABLESPACE y PROFILE son opcionales** : si se omiten, se asignan el tablespace por defecto y el temporal por defecto de la base de datos y el perfil DEFAULT. Por tanto, CREATE USER sin esas cláusulas crea el usuario correctamente. 

- Matiz: la contraseña se escribe sin comillas o entre comillas dobles ("Rosa22"). Entre comillas simples ('ROSA22') Oracle devuelve ORA-00988 (contraseña no válida). 

- El usuario recién creado no puede conectarse hasta que se le conceda el privilegio CREATE SESSION (o el rol CONNECT). 

**Perfiles:** limitan recursos y definen la política de contraseñas. Valores del perfil **DEFAULT** (desde Oracle 11g): 

|**Parámetro**|**Valor por**<br>**defecto**|**Significado**|
|---|---|---|
|**PASSWORD_LIFE_TIME**|180|Días de validez de la contraseña<br>antes de caducar|
|**PASSWORD_GRACE_TIME**|7|Días de gracia tras caducar|
|**FAILED_LOGIN_ATTEMPTS**|10|Intentos fallidos antes de bloquear<br>la cuenta|
|**PASSWORD_LOCK_TIME**|1|Días de bloqueo tras superar los<br>intentos|
|**PASSWORD_REUSE_TIME /**<br>**MAX**|UNLIMITED|Reutilización de contraseñas|



Por ello, con el perfil por defecto sin modificar, la contraseña caduca a los **180 días** . Para cuentas de aplicación suele crearse un perfil específico con PASSWORD_LIFE_TIME UNLIMITED. 

**Roles predefinidos:** 

- **CONNECT:** permite conectarse (desde 10gR2 solo contiene CREATE SESSION). 

- **RESOURCE:** permite crear objetos en el propio esquema (CREATE TABLE, SEQUENCE, PROCEDURE, TRIGGER, TYPE…). 

- **DBA:** todos los privilegios de administración. No debe concederse a usuarios de aplicación (principio de mínimo privilegio). 

El mínimo habitual para el esquema de una aplicación es **CONNECT y RESOURCE** (desde 12c, RESOURCE ya no otorga UNLIMITED TABLESPACE, por lo que hay que asignar cuota en el tablespace). 

```
GRANT CONNECT, RESOURCE TO ROSA;
```

# **8.3.1.5. Arranque y parada de la base de datos** 

**Arranque (STARTUP):** NOMOUNT (arranca la instancia leyendo el fichero de parámetros) → MOUNT (lee los ficheros de control) → OPEN (abre datafiles y redo logs). 

**Parada (SHUTDOWN):** existen cuatro modos: 

|**Modo**|**Comportamiento**|
|---|---|
|**SHUTDOWN NORMAL**|Modo por defecto. No admite nuevas conexiones y espera<br>a que todos los usuarios se desconecten.|
|**SHUTDOWN**<br>**TRANSACTIONAL**|No admite nuevas conexiones ni transacciones; espera a<br>que terminen las transacciones en curso y desconecta a<br>los usuarios.|
|**SHUTDOWN IMMEDIATE**|Deshace (rollback) las transacciones no confirmadas y<br>desconecta a los usuarios inmediatamente. Parada<br>limpia.|



**SHUTDOWN ABORT** Detiene la instancia al instante sin rollback ni checkpoint. Requiere recuperación de la instancia en el siguiente arranque. 

# No existen SHUTDOWN ROLLBACK ni SHUTDOWN BACKGROUND. 

# **8.3.1.6. Recuperación tras una parada abrupta: redo log y ARCHIVELOG** 

- Al hacer COMMIT, LGWR escribe los cambios en el **redo log** en disco; los bloques modificados se escriben en los **datafiles** más tarde (DBWn). Por eso los datafiles pueden no contener todavía cambios confirmados. 

- Tras una caída, SMON realiza la **recuperación de la instancia** : aplica el redo (roll forward) para recuperar las transacciones con COMMIT y usa el undo para deshacer las no confirmadas. 

- En modo **ARCHIVELOG** , el proceso ARCn copia cada redo log lleno a un **redo log archivado** antes de reutilizarlo. Esto permite la recuperación completa de medios y hasta un punto en el tiempo, y copias en caliente. En modo NOARCHIVELOG solo se puede restaurar hasta el último backup completo. Para minimizar pérdidas de datos, las BD de producción deben funcionar en modo ARCHIVELOG. 

- La **SGA** es memoria volátil (se pierde en la caída) y el tablespace **TEMP** solo guarda datos temporales (ordenaciones); TEMPDB es la base de datos temporal de SQL Server, no de Oracle. Ninguno sirve para recuperar datos confirmados. 

```
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;
```

# **8.3.1.7. Herramientas de Oracle** 

- **SQL*Plus:** herramienta de línea de comandos para ejecutar SQL, PL/SQL y comandos propios (CONNECT, STARTUP, SHUTDOWN, DESCRIBE, SPOOL, SET, @script) de forma interactiva o mediante scripts. Otras: SQL Developer (gráfica) y SQLcl. 

- **RMAN (Recovery Manager):** copias de seguridad **físicas** y recuperación de la base de datos completa, tablespaces o datafiles; admite copias incrementales. 

- **Data Pump (expdp / impdp):** exportación e importación **lógica** a nivel de base de datos completa (FULL), **esquema (SCHEMAS)** , tablas o tablespaces. Es la herramienta adecuada para una copia sencilla y rápida de un solo esquema. Sustituye a las antiguas exp/imp. (orabackup o bora no son herramientas de Oracle.) 

```
expdp system SCHEMAS=ROSA DIRECTORY=DATA_PUMP_DIR DUMPFILE=rosa.dmp
LOGFILE=rosa.log
```

- **AWR (Automatic Workload Repository):** repositorio que toma instantáneas periódicas (por defecto cada hora, con retención de 8 días) de estadísticas de rendimiento: uso de recursos, eventos y **tiempos de espera** , y **estadísticas de** 

**ejecución de sentencias SQL** (top SQL). Sus informes (awrrpt.sql) permiten identificar cuellos de botella. Se complementa con **ADDM** (diagnóstico automático a partir de AWR) y **ASH** (muestreo de sesiones activas). Alternativa gratuita: Statspack. 

- **alert.log:** fichero de alertas de la base de datos. Registra de forma cronológica **errores** (ORA-600, ORA-1578…), **advertencias** y **eventos importantes** : arranques y paradas, cambios de redo log, cambios estructurales (ALTER DATABASE, CREATE TABLESPACE), parámetros no por defecto al arrancar, etc. NO registra todas las sentencias SQL (eso es auditoría), ni las conexiones de usuarios (auditoría / listener.log), ni informes periódicos de rendimiento (AWR). Se encuentra en el directorio de diagnóstico ADR. 

# **8.3.1.8. Alta disponibilidad y almacenamiento** 

- **Oracle ASM (Automatic Storage Management):** gestor de volúmenes y sistema de ficheros integrado para ficheros de Oracle. Agrupa discos en **grupos de discos** , distribuye automáticamente los datos entre todos ellos (striping), ofrece espejo (redundancia normal, alta o externa) y reequilibra al añadir o quitar discos. Simplifica la gestión del almacenamiento y mejora rendimiento y disponibilidad. 

- **Oracle RAC (Real Application Clusters):** varias instancias en distintos servidores acceden a una misma base de datos en almacenamiento compartido. Aporta alta disponibilidad y escalabilidad de la instancia. 

- **Oracle Data Guard:** mantiene una o varias bases de datos standby (física o lógica) sincronizadas con la principal, para recuperación ante desastres. 

- **Oracle Data Pump:** exportación/importación lógica de datos (ver punto anterior). 

# **8.3.1.9. Database Links** 

Un **database link** es un objeto de esquema que permite, desde una base de datos Oracle, **acceder a datos (y objetos) de otra base de datos** remota como si fueran locales. Puede ser privado o público y también conectar con SGBD no Oracle mediante Heterogeneous Services / Gateways. Las transacciones que modifican datos en varias bases usan el protocolo de confirmación en dos fases (two-phase commit). 

```
CREATE DATABASE LINK enlace_hosp
  CONNECT TO usuario IDENTIFIED BY clave USING 'HOSPITAL';
SELECT * FROM pacientes@enlace_hosp;
```

# **8.3.1.10. SQL*Plus: SET FEEDBACK** 

SET FEEDBACK controla el mensaje que muestra SQL*Plus tras ejecutar cada sentencia. SET FEEDBACK ON (equivale a umbral 1) muestra «n filas actualizadas/suprimidas/creadas» tras cada sentencia SQL DML ejecutada directamente; por defecto el umbral es 6 filas. Con SET FEEDBACK OFF no se muestra. 

En un **bloque PL/SQL** (BEGIN … END; /) SQL*Plus no muestra el número de filas de las sentencias internas, sino solo el mensaje «Procedimiento PL/SQL terminado correctamente». Ejemplo: un script con UPDATE, un bloque PL/SQL con un DELETE y otro 

DELETE fuera del bloque muestra **2 mensajes de filas** (el del UPDATE y el del último DELETE) más el mensaje del bloque PL/SQL.

# **9. Seguridad e Integridad en Bases de Datos** 

La **seguridad e integridad en bases de datos** son dos conceptos fundamentales para garantizar que la información almacenada en un sistema de gestión de bases de datos (SGBD) esté protegida y se mantenga en un estado consistente. 

- **La seguridad** se enfoca en la **protección de los datos contra accesos no autorizados, pérdida o alteración maliciosa** . 

- **La integridad** garantiza que los datos sean **precisos, coherentes y confiables** , evitando inconsistencias. 

Para lograr estos objetivos, los SGBD implementan diferentes mecanismos que incluyen **controles de acceso, encriptación, auditorías, reglas de integridad y gestión de transacciones** . 

# **9.1. Seguridad en Bases de Datos** 

La **seguridad en bases de datos** protege la información contra accesos no autorizados y posibles ataques. Existen varios niveles de seguridad: 

# **9.1.1. Control de Acceso a Datos** 

Los SGBD utilizan mecanismos de control de acceso para **restringir el acceso a los datos** y garantizar que solo los usuarios autorizados puedan realizar ciertas operaciones. 

**Métodos de autenticación** : 

- **Usuario y contraseña:** La forma más común de autenticación. 

- **Autenticación basada en tokens:** Uso de claves temporales generadas dinámicamente. 

- **Autenticación multifactor (MFA):** Combina usuario/contraseña con códigos de verificación o biometría. 

# **Gestión de permisos con DCL (Data Control Language)** : 

- **GRANT** : Asigna permisos a usuarios. 

- **REVOKE** : Revoca permisos previamente concedidos. 

**Ejemplo de asignación de permisos en SQL** : 

GRANT SELECT, INSERT ON Empleados TO usuario1; REVOKE INSERT ON Empleados FROM usuario1; 

Esto permite que **usuario1** pueda consultar (SELECT) e insertar (INSERT) datos en la tabla **Empleados** , pero si se revoca el permiso de INSERT, solo podrá consultar. 

# **9.1.2. Cifrado de Datos** 

El **cifrado** protege la información almacenada en la base de datos para que, incluso si un atacante accede a los datos, no pueda leerlos sin la clave adecuada. 

**Tipos de cifrado en bases de datos** : 

- **Cifrado a nivel de columna:** Protege datos sensibles como contraseñas o números de tarjetas de crédito. 

- **Cifrado a nivel de base de datos:** Protege toda la base de datos (ejemplo: TDE en Oracle). 

- **Cifrado en tránsito:** Protege los datos cuando viajan por la red (SSL/TLS). 

**Ejemplo de cifrado en MySQL** : 

ALTER TABLE Clientes MODIFY COLUMN DNI VARBINARY(255); 

Esto convierte la columna **DNI** en datos encriptados. 

# **9.1.3. Auditoría y Monitoreo** 

El **monitoreo y la auditoría** permiten registrar las acciones realizadas en la base de datos para detectar accesos sospechosos o intentos de manipulación de datos. 

**Herramientas de auditoría en SGBD** : 

- **SQL Server Audit Logs** : Registra accesos y modificaciones. 

- **Oracle Audit Vault** : Detecta intentos de intrusión. 

- **MySQL General Log** : Rastrea consultas ejecutadas. 

**Ejemplo de auditoría en SQL Server** : 

CREATE SERVER AUDIT AuditoriaBD TO FILE ( FILEPATH = 'C:\Auditoria\' ); 

CREATE DATABASE AUDIT SPECIFICATION AuditoriaEmpleados FOR SERVER AUDIT AuditoriaBD ADD (SELECT, INSERT, UPDATE ON Empleados BY usuario1); 

Esto guarda un registro de las acciones de **usuario1** en la tabla **Empleados** . 

# **9.1.4. Protección contra Ataques** 

Las bases de datos son vulnerables a ataques, por lo que se deben implementar medidas de protección. 

**Principales amenazas y contramedidas** : 

|**Amenaza**|**Descripción**|**Solución**|
|---|---|---|
|**SQL Injection**|Un atacante introduce código<br>SQL malicioso en consultas.|Usar**consultas parametrizadas**.|
|**Acceso no**<br>**autorizado**|Un usuario obtiene acceso sin<br>permisos.|Implementar**autenticación**<br>**fuerte y permisos mínimos**.|
|**Robo de datos**|Un intruso accede a datos<br>sensibles.|Usar**cifrado y auditoría**.|



**Ejemplo de prevención de SQL Injection en PHP con MySQL** : 

$stmt = $conn->prepare("SELECT * FROM usuarios WHERE email = ?"); $stmt->bind_param("s", $email); $stmt->execute(); 

Aquí **no se permite que el usuario introduzca código SQL malicioso** . 

# **9.2. Integridad en Bases de Datos** 

La **integridad en bases de datos** garantiza que los datos sean consistentes y precisos, evitando errores y anomalías. 

# **9.2.1. Reglas de Integridad** 

Los SGBD aplican **reglas de integridad** para prevenir inconsistencias en los datos. 

# 1. **Integridad de Entidad:** 

- La clave primaria no puede ser nula ni repetida. 

- Ejemplo en SQL: 

CREATE TABLE Empleados ( ID INT PRIMARY KEY, Nombre VARCHAR(50) NOT NULL ); 

# 2. **Integridad Referencial:** 

- Las claves foráneas deben existir en la tabla referenciada. 

- Ejemplo en SQL: 

CREATE TABLE Departamentos ( ID INT PRIMARY KEY, Nombre VARCHAR(50) NOT NULL ); 

CREATE TABLE Empleados ( ID INT PRIMARY KEY, Nombre VARCHAR(50), ID_Departamento INT, FOREIGN KEY (ID_Departamento) REFERENCES Departamentos(ID) ); 

# 3. **Integridad de Dominio:** 

- Asegura que los valores introducidos sean válidos. 

- Ejemplo en SQL: 

ALTER TABLE Empleados ADD CONSTRAINT chk_Salario CHECK (Salario > 0); 

# **9.2.2. Mecanismos de Integridad** 

Los SGBD ofrecen varias herramientas para garantizar la integridad de los datos. 

# **Restricciones (CONSTRAINTS)** : 

- NOT NULL: Evita valores nulos en un campo. 

- UNIQUE: Garantiza que no haya valores repetidos en una columna. 

- CHECK: Valida condiciones específicas. 

- FOREIGN KEY: Mantiene la integridad referencial. 

**Transacciones y ACID** : Las transacciones permiten agrupar varias operaciones en una unidad lógica de trabajo. 

# **Propiedades ACID** : 

1. **Atomicidad** : Se ejecuta toda la transacción o ninguna. 

2. **Consistencia** : La base de datos siempre pasa de un estado válido a otro. 

3. **Aislamiento** : Cada transacción es independiente. 

4. **Durabilidad** : Una vez confirmada, la transacción no se pierde. 

**Ejemplo de transacción en SQL** : 

# BEGIN TRANSACTION; 

UPDATE Cuentas SET Saldo = Saldo - 500 WHERE ID = 1; UPDATE Cuentas SET Saldo = Saldo + 500 WHERE ID = 2; COMMIT; 

Aquí se transfiere dinero entre cuentas **sin perder datos en caso de error** .
