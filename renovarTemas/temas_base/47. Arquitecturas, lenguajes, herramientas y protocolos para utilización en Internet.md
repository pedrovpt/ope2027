# 1\. Arquitectura y protocolos

  - La arquitectura de una aplicación web consta de tres componentes principales:
    
      - **Servidor web**: distribuye páginas de información formateada a los clientes que las solicitan.
    
      - **Conexión de red**: comunica servidor y clientes mediante el protocolo HTTP.
    
      - **Clientes**: navegador web u otros dispositivos que acceden a la aplicación.

  - Las aplicaciones web siguen el modelo cliente/servidor y se componen de: **lógica de negocio** (procesos y operaciones), **administración de los datos** (BD y archivos) e **interfaz** (acceso del usuario mediante navegador u otros dispositivos).

  - Modelos por capas:
    
      - **Dos capas**: cliente pesado (fat client) con lógica de negocio e interfaz; servidor que administra los datos. Escalabilidad difícil, número de conexiones limitado, alta carga en la red, flexibilidad y funcionalidad limitadas.
    
      - **Tres capas**: presentación (recoge y envía información al servidor, genera y visualiza la presentación), proceso o negocio (procesa la información e interactúa con la capa de datos) y datos (almacena, recupera y mantiene los datos).

### Cliente ligero, cliente pesado y "zero footprint"

  - **Cliente pesado (fat/thick client)**: aplicación que hay que instalar en el puesto y que contiene lógica de negocio (p. ej. un cliente Oracle Forms clásico o una aplicación de escritorio).

  - **Cliente ligero (thin client)**: la lógica reside en el servidor; el puesto solo presenta.

  - **Zero footprint** ("huella cero" en el cliente): la aplicación se consume desde un **navegador web estándar sin instalar nada más** en el equipo (ni plugins, ni applets Java, ni ActiveX, ni agentes). Es el caso de las aplicaciones web HTML5 puras. No tiene nada que ver con la huella de carbono, con vulnerabilidades zero-day ni con Energy Star.

### Servidores web, servidores de aplicaciones y proxy inverso

  - **Servidor web (HTTP)**: sirve recursos por HTTP/HTTPS. Ejemplos: **Apache HTTP Server**, **Nginx**, Microsoft **IIS**, LiteSpeed.

  - **Nginx** (pronunciado "engine-x"): software libre que actúa como **servidor web** de alto rendimiento (arquitectura asíncrona orientada a eventos) y también como **proxy inverso**, balanceador de carga y caché HTTP. No ejecuta Java en el cliente.

  - **Proxy inverso**: servidor que se sitúa delante de uno o varios servidores internos y recibe las peticiones de los clientes en su nombre; aporta balanceo de carga, terminación TLS/SSL, caché, compresión y ocultación de la infraestructura interna. (Un proxy "directo" o forward actúa, al contrario, en nombre de los clientes.)

  - **Servidores de aplicaciones / contenedores**: ejecutan la lógica de servidor. Java: Apache **Tomcat** (contenedor de servlets/JSP), WildFly/JBoss, WebLogic, GlassFish/Payara. .NET: IIS/Kestrel. Node.js incorpora su propio servidor HTTP.

## 1.1 Protocolos

  - **TCP** (Transmission Control Protocol): controla la transmisión de datos de forma fiable y orientada a conexión.

  - **IP** (Internet Protocol): encamina y transmite los paquetes de datos en Internet.

  - **URL** (Uniform Resource Locator): identifica de forma única un recurso en la red con un formato estándar:

\<scheme\>://\<host\>:\<port\>/\<path\>;\<parameters\>?\<query\>\#\<fragment\>

  - **HTTP** (HyperText Transfer Protocol): protocolo de transferencia de información en la World Wide Web. Es un protocolo **sin estado (stateless)**: cada petición es independiente de las anteriores.
    
      - **HTTP/1.1**: en la práctica una petición en curso por conexión, lo que genera latencia; cada recurso (imágenes, scripts…) exige una nueva petición HTTP.
    
      - **HTTP/2**: multiplexación de peticiones sobre la misma conexión, menor latencia y compresión de cabeceras (HPACK).
    
      - **HTTPS** (HTTP Secure): HTTP sobre TLS; cifra las comunicaciones cliente-servidor y se ha vuelto obligatorio en la práctica.
    
      - **HTTP/3**: basado en **QUIC** (sobre UDP), mejora velocidad y seguridad, especialmente en redes móviles.

### Métodos (verbos) HTTP

| **Método** | **Uso**                                                                               | **Seguro** | **Idempotente**     |
| ---------- | ------------------------------------------------------------------------------------- | ---------- | ------------------- |
| GET        | Obtener (leer) un recurso                                                             | Sí         | Sí                  |
| HEAD       | Igual que GET pero solo devuelve cabeceras                                            | Sí         | Sí                  |
| POST       | Crear un recurso / enviar datos a procesar (formularios)                              | No         | No                  |
| PUT        | Actualizar un recurso **sustituyéndolo por completo** (o crearlo en una URI conocida) | No         | Sí                  |
| PATCH      | Actualización **parcial** de un recurso (solo los campos indicados)                   | No         | No (no garantizado) |
| DELETE     | Borrar un recurso                                                                     | No         | Sí                  |
| OPTIONS    | Consultar los métodos admitidos (se usa en el "preflight" CORS)                       | Sí         | Sí                  |

**Seguro** = no modifica el estado del servidor. **Idempotente** = repetir la misma petición produce el mismo resultado que hacerla una vez.

### Códigos de estado HTTP

| **Clase** | **Significado**    | **Códigos más preguntados**                                                                                                                                                                                                                               |
| --------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1xx       | Informativo        | 100 Continue, 101 Switching Protocols (p. ej. paso a WebSocket)                                                                                                                                                                                           |
| 2xx       | Éxito              | 200 OK, 201 Created, 204 No Content                                                                                                                                                                                                                       |
| 3xx       | Redirección        | 301 Moved Permanently, 302 Found (redirección temporal por cambio de ubicación), 304 Not Modified                                                                                                                                                         |
| 4xx       | Error del cliente  | 400 Bad Request (sintaxis de la petición inválida), 401 Unauthorized (falta autenticación), 403 Forbidden (autenticado pero sin permiso), **404 Not Found (el servidor no encuentra el recurso solicitado)**, 405 Method Not Allowed, 408 Request Timeout |
| 5xx       | Error del servidor | 500 Internal Server Error, 501 Not Implemented, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout                                                                                                                                             |

### Cookies y estado de sesión 

  - Como HTTP no guarda estado, se usan **cookies**: pequeños datos que el **servidor (la página web) guarda en el navegador del cliente** para reconocerlo en accesos posteriores (sesión, preferencias, carrito…).

  - El servidor las crea con la cabecera de respuesta Set-Cookie y el navegador las reenvía en cada petición al mismo dominio con la cabecera Cookie.

  - Tipos: **de sesión** (se borran al cerrar el navegador) y **persistentes** (con Expires o Max-Age); **propias** y **de terceros**.

  - Atributos de seguridad: Secure (solo por HTTPS), HttpOnly (no accesible desde JavaScript, mitiga XSS), SameSite (Strict/Lax/None, mitiga CSRF), Domain y Path.

  - El usuario **puede borrarlas y bloquearlas** desde el navegador; también las pueden bloquear antivirus y extensiones. Las cookies no técnicas requieren consentimiento (LSSI/RGPD).

  - Alternativas en el cliente (HTML5): **Web Storage** (localStorage persistente y sessionStorage por pestaña) e IndexedDB.

### Codificación de caracteres: Unicode y UTF

  - **Unicode** asigna un número (punto de código) a cada carácter de cualquier idioma. Se representa en bytes mediante codificaciones:
    
      - **UTF-8**: longitud variable de 1 a 4 bytes, compatible con ASCII. Es la codificación **estándar de la web**, la codificación por defecto de XML y JSON y la que exige la normativa TIC del SAS para informes, plantillas y servicios.
    
      - **UTF-16**: 2 o 4 bytes por carácter (formato interno de las cadenas en Java y JavaScript).
    
      - **UTF-32**: 4 bytes fijos por carácter; simple pero ocupa mucho.
    
      - **SCSU** (Standard Compression Scheme for Unicode): esquema de compresión de texto Unicode, prácticamente sin uso en la web.

  - En HTML se declara con \<meta charset="UTF-8"\>; en XML con \<?xml version="1.0" encoding="UTF-8"?\>.

### Estándares web frente a paradigmas de arquitectura

  - Los **estándares de aplicaciones web** son especificaciones de lenguajes y APIs publicadas por organismos como el **W3C**, WHATWG, IETF o Ecma: HTML5, CSS, XML, DOM, SVG, ECMAScript (JavaScript), HTTP, WebSocket…

  - **SOA** (Service Oriented Architecture) **no es un estándar** de aplicaciones web: es un **paradigma o estilo de arquitectura** basado en servicios débilmente acoplados (ver apartado 8).

# 2\. Lenguajes: HTML y XHTML

## 2.1 HTML (HyperText Markup Language)

  - Lenguaje de marcado que describe el contenido y la estructura de las páginas web. Estándar W3C (hoy mantenido como "HTML Living Standard" por WHATWG); última versión: HTML5.

  - Etiquetas más utilizadas: formato de texto, tablas, listas, contenido incrustado e hiperenlaces.

  - Estándares oficiales: HTML 2.0, HTML 3.2, HTML 4.0, HTML 4.01 (1999) y HTML5 (2014).

  - Mejoras de HTML5:
    
      - **Diseño adaptativo** y compatibilidad móvil.
    
      - **Multimedia nativa**: \<video\> y \<audio\>, sin plugins externos.
    
      - **Nuevas APIs**: Geolocation, Web Storage (local y de sesión), Drag & Drop, Offline Web Apps, Canvas, **WebSocket**, Web Workers…
    
      - **Etiquetas semánticas**: \<section\>, \<article\>, \<header\>, \<footer\>, \<nav\>, además de \<canvas\>, \<svg\>, \<math\> y \<time\>.
    
      - Completan el grupo de etiquetas semánticas de HTML5: **\`\<main\>\`** (contenido principal, uno por página), **\`\<aside\>\`** (contenido complementario/lateral), **\`\<figure\>\`** y **\`\<figcaption\>\`** (ilustraciones, diagramas o imágenes con pie), \<mark\>, \<details\>/\<summary\> y \<address\>. Tanto \<article\>, \<section\>, \<footer\> como \<main\>, \<nav\>, \<aside\> son etiquetas semánticas.
    
      - **Elementos obsoletos**: \<font\> y \<center\> (la presentación se delega en CSS).

## 2.2 Sintaxis básica de HTML

  - Un **elemento** = etiqueta de apertura + contenido + etiqueta de cierre: \<p\>Texto\</p\>.

  - Los **elementos pueden anidarse** (un elemento dentro de otro), siempre que se cierren en orden inverso, sin solaparse: \<p\>\<strong\>bien\</strong\>\</p\>.

  - **Elementos vacíos**: no tienen contenido ni etiqueta de cierre: \<br\>, \<hr\>, \<img\>, \<input\>, \<meta\>, \<link\>. **Pueden tener atributos** aunque no tengan contenido.

  - Los **atributos** van siempre en la **etiqueta de apertura**, nunca en la de cierre, con la forma nombre="valor". En HTML las comillas son opcionales si el valor no contiene espacios (\<table class=listado\> es válido); en XHTML son obligatorias.

  - **Atributos globales** (válidos en cualquier elemento): id (identificador único), **\`class\`** (una o varias clases CSS), style (estilo en línea), title, lang, hidden, tabindex, data-\*. Ejemplo: \<table class="listado"\> indica que la tabla es de clase "listado"; \<table id="listado"\> le da el identificador "listado".

  - **Nombres de etiquetas y atributos no distinguen mayúsculas/minúsculas** en la sintaxis HTML (\<P\> = \<p\>); en XML/XHTML sí se distinguen.

  - Declaración de documento HTML5: \<\!DOCTYPE html\> (ya no referencia ninguna DTD).

### Modelo de contenido: qué se puede anidar dentro de qué

  - Contenido de **flujo** (bloques como \<div\>, \<p\>, \<section\>, \<figure\>, \<table\>) y contenido de **fraseo** (en línea: \<span\>, \<a\>, \<strong\>, \<em\>, \<img\>).

  - \<span\> solo admite contenido de fraseo: **incluir un \`\<p\>\` dentro de un \`\<span\>\` contraviene HTML5**. En cambio \<p\> o \<span\> dentro de \<div\> es correcto.

  - \<p\> no puede contener bloques (\<div\>, \<ul\>, \<table\>, otro \<p\>).

  - Enmarcar una imagen (propia o externa) con \<figure\> + \<figcaption\> es correcto; modificar el href de un enlace con JavaScript también. El elemento \<style\> se coloca normalmente en \<head\>; los navegadores lo procesan también en el cuerpo, y HTML 5.2 del W3C lo admitía en contenido de flujo, por lo que en examen no se considera la infracción.

### Enlaces e imágenes

  - Hiperenlace: \<a href="URL"\>texto\</a\>. El atributo **\`href\`** indica el destino del enlace (sin href el enlace no navega). No existen atributos url ni link en \<a\>, ni etiquetas \<href\>/\<target\>.

  - **\`target\`** indica dónde abrir el destino: \_blank (nueva ventana/pestaña), \_self (misma, por defecto), \_parent, \_top. Un valor sin guion bajo (target="blank") funciona como nombre de ventana. Un enlace puede envolver una imagen:

\<a target="\_blank" href="http://www.myhospital.com"\>\<img src="hospitalicon.png" alt="Hospital"\>\</a\>

  - Imagen: \<img src="ruta" alt="texto alternativo"\>. El atributo **\`alt\`** es el **texto alternativo** que leen los lectores de pantalla y se muestra si la imagen no carga; es obligatorio para la accesibilidad (WCAG 2.x, criterio 1.1.1, nivel A). title solo muestra un tooltip.

### Formularios

  - \<form action="url" method="get|post"\> agrupa los controles. Controles: \<input\>, **\`\<select\>\` con \`\<option\>\`** (lista desplegable), \<textarea\>, \<button\>, \<label\>, \<fieldset\>/\<legend\>.

  - Tipos del atributo type de \<input\>:

| **Grupo**         | **Valores de type**                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| Clásicos (HTML 4) | text, password, checkbox, radio, submit, reset, button, hidden, image, **\`file\`**            |
| Nuevos HTML5      | email, url, tel, number, range, search, color, **\`date\`**, time, datetime-local, month, week |
| NO existen        | **\`select\`** (es un elemento propio, no un type), textarea, list, datetime (obsoleto)        |

  - **Subir ficheros**: \<input type="file"\>; el formulario debe usar method="post" y enctype="multipart/form-data".

  - **Selector de fechas**: \<input type="date"\> (el navegador muestra un calendario).

  - Validación nativa HTML5: atributos required, pattern (expresión regular), min, max, maxlength, placeholder.

### API WebSocket 

  - **WebSocket** es un protocolo (RFC 6455) y una API estándar que establece un **canal bidireccional full-duplex y persistente** sobre una conexión TCP. Se inicia con una petición HTTP que se "actualiza" (Upgrade, código 101). Esquemas: ws:// y wss:// (cifrado TLS).

  - Eventos del objeto: open, **\`message\`**, error, close. Métodos: send() y close(). El dato recibido está en evento.data.

const socket = new WebSocket("wss://servidor.sas.es/chat");

socket.addEventListener("open", () =\> socket.send("Hola"));

socket.addEventListener("message", (evento) =\> { alert(evento.data); });

// equivalente: socket.onmessage = (evento) =\> alert(evento.data);

## 2.3 XHTML (eXtensible HyperText Markup Language)

  - Versión más estricta de HTML reformulada como XML, para favorecer la extensibilidad y la interoperabilidad.

  - Los documentos XHTML están bien formados, por lo que pueden analizarse con parsers XML estándar. Última versión: XHTML 1.1.

  - Diferencias con HTML: los elementos vacíos se cierran (\<br /\>), los valores de atributos van entre comillas y los nombres de elementos y atributos van en minúsculas.

# 3\. CSS (Cascading Style Sheets)

  - Describe la presentación de documentos HTML o XML y permite separar contenido y presentación.

  - Formas de uso:
    
      - **En línea (inline)**: atributo style del elemento.
    
      - **Interna**: \<style\>…\</style\> dentro de \<head\>.
    
      - **Externa**: \<link rel="stylesheet" href="hoja\_estilos.css"\>.

  - **CSS3**: bordes redondeados, múltiples imágenes de fondo, animaciones, tipografías web (@font-face).

## 3.1 Sintaxis y selectores

  - Una regla CSS = **selector** + bloque de declaraciones propiedad: valor;:

selector { propiedad: valor; propiedad2: valor2; }

| **Selector**           | **Ejemplo**                                                | **Selecciona**                                                             |
| ---------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| Universal              | \* { }                                                     | Todos los elementos                                                        |
| **De etiqueta (tipo)** | span { text-decoration: underline; }                       | Todos los elementos de ese tipo concreto (todos los span)                  |
| **De clase**           | .listado { } / table.listado { }                           | Elementos con class="listado" (solo tablas en el 2º caso)                  |
| **De ID**              | \#listado { } / table\#listado { background-color: blue; } | El elemento con id="listado" (la tabla cuyo id es listado, con fondo azul) |
| **De atributo**        | input\[type="text"\] { }                                   | Elementos con ese atributo/valor                                           |
| **Agrupación**         | ul, ol { color: red; }                                     | Aplica la misma regla a varios selectores: listas ul y ol en rojo          |
| Descendiente / hijo    | div p { } / div \> p { }                                   | p dentro de div (a cualquier nivel / hijo directo)                         |
| Pseudoclase            | a:hover, a:visited, input:focus                            | Estados de un elemento                                                     |
| Pseudoelemento         | p::first-line, a::before                                   | Partes de un elemento                                                      |

  - **Especificidad** (de mayor a menor): estilo en línea \> ID \> clase/atributo/pseudoclase \> etiqueta. \!important prevalece sobre todas.

## 3.2 Colores en CSS

| **Notación**        | **Ejemplos válidos**                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------------------- |
| Nombre              | red, blue, transparent                                                                                      |
| Hexadecimal         | \#0f0 (3 dígitos), **\`\#00fc\`** (4 dígitos = RGB + alfa), \#00ff00 (6), \#00ff00cc (8)                    |
| rgb() / rgba()      | rgb(0, 255, 0), **\`rgb(0 255 0)\`** (sintaxis moderna con espacios), rgb(0 255 0 / 50%), rgba(0,255,0,0.5) |
| hsl() / hsla()      | **\`hsl(120deg 100% 50%)\`**, hsl(120, 100%, 50%), hsla(120,100%,50%,0.3)                                   |
| Otras (CSS Color 4) | hwb(), lab(), lch(), oklch(), color()                                                                       |
| NO existe           | **\`argb()\`** (el orden ARGB es de Android/.NET, no de CSS)                                                |

## 3.3 Modelo de caja y propiedades frecuentes

  - Cada elemento es una caja: **content** → **padding** (margen interno) → **border** → **margin** (margen externo).

  - **padding / margin abreviados** admiten de **1 a 4 valores**, en el sentido de las agujas del reloj:

| **Valores**                      | **Significado**                               |
| -------------------------------- | --------------------------------------------- |
| padding: 10px;                   | Los 4 lados                                   |
| padding: 10px 5px;               | Arriba-abajo | izquierda-derecha              |
| padding: 10px 5px 20px;          | Arriba | izquierda-derecha | abajo            |
| padding: 1em 5px 20px 10px;      | Arriba | derecha | abajo | izquierda          |
| padding: 1em 5px 20px 10px 30px; | **Incorrecto**: 5 valores no están permitidos |

  - **text-decoration**: underline (subrayado), none, line-through, overline. Para subrayar todos los span: span { text-decoration: underline; }.

  - **outline**: línea que el navegador dibuja alrededor del elemento que tiene el foco (el recuadro punteado de los enlaces al hacer clic). Se elimina con a { outline: 0; } o outline: none. No existe la propiedad link. Ojo: por accesibilidad (WCAG 2.4.7, foco visible, nivel AA) conviene sustituirlo por otro indicador de foco en lugar de eliminarlo sin más.

  - Otras: color, background-color, font-family, font-size, font-weight, display (block, inline, flex, grid, none), position, width/height.

## 3.4 Frameworks de diseño web (front-end)

  - **Bootstrap** (Twitter): framework CSS/JS responsive basado en rejilla de 12 columnas.

  - **Materialize**: framework CSS basado en **Material Design** de Google.

  - **jQuery UI**: biblioteca de widgets (datepicker, diálogos, pestañas, autocompletar) y efectos sobre jQuery.

  - Otros: Foundation, Bulma, Tailwind CSS, Angular Material.

  - **Oracle Forms NO es un framework de diseño web**: es una herramienta de Oracle para construir aplicaciones de formularios sobre base de datos (tradicionalmente cliente/servidor o mediante applet Java), por lo que no sirve para diseñar una web responsive de acceso ciudadano.

# 4\. XML (eXtensible Markup Language)

  - Lenguaje de marcado que describe el contenido de forma independiente de la presentación. Deriva de SGML. Última versión: XML 1.1.

  - Muchas APIs (servicios web SOAP y algunas REST) usan XML como formato de intercambio, aunque JSON ha ganado popularidad por ser más ligero.

  - Las etiquetas XML son **case sensitive** y los valores de los atributos van **siempre entre comillas**.

## 4.1 Partes de un documento XML

  - **Prólogo** (opcional): declaración XML, declaración del tipo de documento (DOCTYPE), comentarios e instrucciones de procesamiento.

  - **Cuerpo** (obligatorio): un **único elemento raíz**.

  - **Elementos**: con contenido o vacíos. **Atributos**: propiedades de los elementos (entre comillas). Funcionan como metadatos del elemento.

  - **Entidades predefinidas**: representan caracteres especiales para que no se interpreten como marcado: \&lt; (\<), \&gt; (\>), \&amp; (&), \&quot; ("), \&apos; (').

  - **Secciones CDATA**: \<\!\[CDATA\[ … \]\]\>, texto que no se interpreta como marcado. **Comentarios**: \<\!-- … --\>, ignorados por el procesador.

## 4.2 Documentos bien formados y válidos

  - **Bien formado**: sintaxis correcta según la especificación: declaración XML, un único elemento raíz, elementos cerrados y correctamente anidados, atributos entre comillas, distinción de mayúsculas/minúsculas.

  - **Válido**: además de bien formado, cumple una **DTD** o un **XML Schema**.

## 4.3 Validación: DTD y XML Schema

  - **DTD** (Document Type Definition): describe la estructura y sintaxis; define elementos, atributos y entidades permitidos. Puede ser externa o estar incrustada en el propio documento.

### Sintaxis de una DTD

\<\!ELEMENT nombre (contenido)\>

\<\!ELEMENT nombre (\#PCDATA)\> \<\!-- texto --\>

\<\!ELEMENT br EMPTY\> \<\!-- elemento vacío --\>

\<\!ELEMENT libre ANY\> \<\!-- cualquier contenido --\>

\<\!ATTLIST paciente id CDATA \#REQUIRED sexo (H|M) \#IMPLIED\>

\<\!ENTITY sas "Servicio Andaluz de Salud"\>

| **Símbolo**                      | **Cardinalidad / significado**                   |
| -------------------------------- | ------------------------------------------------ |
| (ninguno)                        | Exactamente una vez: (nombre)                    |
| ?                                | Opcional: 0 o 1 vez: telefono?                   |
| \*                               | 0 o más veces                                    |
| \+                               | 1 o más veces: paciente+                         |
| ,                                | Secuencia en ese orden: (nombre, dni, telefono?) |
| |                                | Alternativa (uno u otro)                         |
| \#REQUIRED / \#IMPLIED / \#FIXED | Atributo obligatorio / opcional / con valor fijo |

Ejemplo de examen: con \<\!ELEMENT listapacientes (paciente+)\> y \<\!ELEMENT paciente (nombre, dni, telefono?)\>, son correctas una lista con uno o varios pacientes que tengan nombre y dni, con o sin teléfono: por eso los tres XML propuestos se consideran válidos. (Matiz: en esa DTD se declara direccion pero no telefono; un parser validador estricto lo señalaría, pero la respuesta oficial es "todos son válidos" atendiendo a la cardinalidad.)

  - **XML Schema** (XSD): documento XML que define elementos y atributos permitidos en otro XML. Ventajas sobre DTD: sintaxis XML, definición de nuevos tipos de datos, herencia entre tipos y soporte de namespaces.

## 4.4 Procesamiento de XML

  - **DOM**: crea un árbol de objetos en memoria que permite manipular el documento.

  - **SAX**: procesa el documento de forma secuencial por eventos, eficiente en memoria.

### Ejemplo de documento XML

\<?xml version="1.0" encoding="UTF-8"?\>

\<\!-- Ejemplo de documento XML --\>

\<libro\>

\<titulo\>Introducción a XML\</titulo\>

\<autor nombre="Juan Pérez" edad="35"\>\</autor\>

\<fecha\_publicacion\>2024-01-01\</fecha\_publicacion\>

\<descripcion\>El libro cubre XML \&amp; JSON.\</descripcion\>

\<comentarios\>\<\!\[CDATA\[Texto libre, no se procesa como XML.\]\]\>\</comentarios\>

\<capitulos\>

\<capitulo numero="1"\>\<titulo\>Introducción\</titulo\>\</capitulo\>

\<capitulo numero="2"\>\<titulo\>Elementos y Atributos\</titulo\>\</capitulo\>

\</capitulos\>

\</libro\>

## 4.5 XSL (eXtensible Stylesheet Language)

Conjunto de estándares W3C para dar formato y transformar documentos XML:

  - **XSLT**: transforma un XML en otro formato (HTML, texto, otro XML…) mediante plantillas y reglas que se aplican cuando los nodos coinciden.

  - **XPath**: lenguaje de expresiones para recorrer un XML y seleccionar nodos.

  - **XSL-FO**: especifica el formato de presentación (p. ej. para generar PDF).

  - **XQuery**: lenguaje de consulta sobre datos XML.

  - **XLink**: define enlaces entre documentos, imágenes y archivos. **XPointer**: direcciona fragmentos de un XML, basado en XPath.

## 4.6 Lenguajes basados en XML

  - Sindicación de contenidos: **RSS** (distribución de contenido actualizado, como noticias) y Atom. **RDF**: base de la web semántica (tripletas sujeto-predicado-objeto).

  - **XBRL**: estándar XML para información contable, financiera y tributaria.

  - **SOAP** y **WSDL** (servicios web, apartado 8), **SVG** (gráficos vectoriales), **MathML**, **XHTML**, **HL7 CDA** (documentos clínicos).

## 4.7 JSON y comparación con XML

  - **JSON** (JavaScript Object Notation): formato ligero de intercambio de datos, alternativa más simple a XML.

  - Definido en RFC 8259 / ECMA-404; tipo MIME application/json; codificación UTF-8. Tipos: cadena (siempre entre **comillas dobles**), número, booleano, null, objeto { } y array \[ \]. No admite comentarios ni atributos.

  - **Ni XML ni JSON son lenguajes de programación**: XML es un lenguaje de marcado y JSON un formato de datos. XML permite metadatos mediante atributos; JSON no tiene atributos.

  - Ambos son **formatos de texto**. Para transportar **datos binarios** (una fotografía, un PDF) se codifican en **Base64** dentro de un campo JSON o XML, o se envían como multipart/form-data; por tanto la imagen puede enviarse con cualquiera de ellos.

| **Aspecto**             | **XML**                                | **JSON**                        |
| ----------------------- | -------------------------------------- | ------------------------------- |
| Naturaleza              | Lenguaje de marcado extensible         | Formato de intercambio de datos |
| Verbosidad              | Mayor (etiquetas de apertura y cierre) | Menor, más ligero               |
| Validación              | DTD / XML Schema                       | JSON Schema                     |
| Consulta/transformación | XPath, XQuery, XSLT                    | JSONPath; nativo en JavaScript  |
| Atributos/metadatos     | Sí                                     | No                              |
| Comentarios             | Sí                                     | No                              |

# 5\. Desarrollo de aplicaciones web en el cliente y en el servidor

  - **Servlets**: evolución de los CGI; programas Java que generan contenido dinámico y se ejecutan en el motor de servlets del servidor. Crean un **hilo** por petición (no un proceso), por lo que son más eficientes; parte de J2EE. A diferencia de los applets, no tienen restricciones de seguridad (pueden acceder a ficheros del servidor).

  - **XML y XSL**: XML para compartir datos entre plataformas y XSL para darles formato.

  - **Applets de Java**: pequeños programas que se ejecutaban dentro del navegador, sin ejecución independiente y con privilegios restringidos (tecnología obsoleta y hoy sin soporte en los navegadores).

### PHP: acceso a MySQL y JSON

Parámetros básicos: **dirección del servidor**, **usuario y contraseña** (la BD es opcional). Devuelve el objeto de conexión o false. Estilo orientado a objetos: new mysqli(...). Alternativa genérica: **PDO**.

if (\!$con) { die("Error: " . mysqli\_connect\_error()); }

  - **\`json\_decode($json, true)\`** convierte una cadena JSON en un **array asociativo** (con false o sin segundo parámetro devuelve un objeto stdClass). La inversa es **\`json\_encode()\`**.

## 8\. Servicios web: SOA, SOAP, WSDL y REST

  - Un **servicio web** es un componente software accesible por red mediante protocolos estándar, que permite la interoperabilidad entre aplicaciones de distintas plataformas.

  - **SOA** (Arquitectura Orientada a Servicios): **paradigma de arquitectura**, no un estándar ni un lenguaje. Organiza los sistemas como servicios reutilizables, débilmente acoplados y con contratos bien definidos. Se implementa con servicios SOAP/WSDL o REST, a menudo con un bus de servicios (ESB).

### Servicios web SOAP 

  - **SOAP** (Simple Object Access Protocol): **protocolo** del W3C que **especifica el formato de los mensajes** (en XML) que se intercambian los servicios. Independiente del transporte (normalmente HTTP/HTTPS, también SMTP o JMS).

  - **Estructura de un mensaje SOAP**:
    
      - **Envelope** (sobre): **obligatorio**, elemento raíz.
    
      - **Header** (cabecera): **opcional**; información de seguridad (WS-Security), transacciones, direccionamiento.
    
      - **Body** (cuerpo): **obligatorio**; contiene la petición o la respuesta.
    
      - **Fault**: opcional, dentro del Body, para informar de errores.

\<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"\>

\<soap:Header\> ... \</soap:Header\> \<\!-- opcional --\>

\<soap:Body\> \<\!-- obligatorio --\>

\<m:ObtenerPaciente\>\<m:nuhsa\>AN0123456789\</m:nuhsa\>\</m:ObtenerPaciente\>

\</soap:Body\>

\</soap:Envelope\>

  - **WSDL** (Web Services Description Language): **lenguaje basado en XML que describe un servicio web**: qué operaciones publica, los mensajes y tipos de datos de entrada/salida, el protocolo de enlace (binding) y la dirección (endpoint). Elementos: types, message, portType (interface en WSDL 2.0), binding, port (endpoint) y service. Es el "contrato" del servicio.

  - **UDDI**: registro/directorio para publicar y descubrir servicios web.

### Servicios REST

  - **REST** (Representational State Transfer): estilo de arquitectura definido por Roy Fielding (2000). No es un protocolo; se apoya en HTTP.

  - Principios: cliente-servidor, **sin estado (stateless)** (cada petición lleva toda la información necesaria), cacheable, interfaz uniforme, sistema en capas y código bajo demanda (opcional).

  - Los **recursos** se identifican por **URI** y se manipulan con los **métodos HTTP**; los datos se intercambian normalmente en **JSON** (también XML). La seguridad se consigue con **HTTPS** y tokens (OAuth 2.0, JWT).

| **Operación CRUD**           | **Método HTTP** | **Ejemplo**                                         |
| ---------------------------- | --------------- | --------------------------------------------------- |
| Leer                         | **GET**         | GET /pacientes/15                                   |
| Crear                        | **POST**        | POST /pacientes                                     |
| Actualizar (objeto completo) | **PUT**         | PUT /pacientes/15                                   |
| Actualizar parcialmente      | **PATCH**       | PATCH /pacientes/15 con solo los campos que cambian |
| Borrar                       | **DELETE**      | DELETE /pacientes/15                                |

  - Comparación: SOAP es un protocolo rígido basado en XML con contrato WSDL; REST es un estilo ligero sobre HTTP, con JSON habitualmente y descripción opcional mediante **OpenAPI/Swagger**.

# 9\. JavaScript, XMLHttpRequest y AJAX

  - Los lenguajes de cliente se ejecutan en el navegador. HTML estructura el contenido, pero la interactividad la aportan los scripts, principalmente JavaScript, que el navegador interpreta con su motor.

  - Son independientes del servidor; si el navegador no soporta el script o tiene fallos de seguridad, no se disfruta de la interactividad y puede haber vulnerabilidades.

## 9.1 DOM (Document Object Model)

  - Representa la estructura de un documento HTML o XML y permite manipular contenido, estructura y estilo.

  - Los objetos tienen propiedades y reaccionan a eventos (clic, movimiento del ratón…). Se accede a ellos con funciones como getElementById, querySelector.

  - Fases de un evento: **captura** (baja hasta el destino), **objetivo/blanco** (llega al destino) y **burbujeo** (sube de nuevo). Se gestionan con manejadores de eventos (addEventListener).

  - Frameworks y bibliotecas como jQuery, Prototype o AngularJS simplifican el manejo del DOM, los eventos y las animaciones.

## 9.2 Fundamentos del lenguaje JavaScript

### Variables e identificadores

  - Declaración: **\`var\`** (ámbito de función, con hoisting, redeclarable), **\`let\`** (ámbito de bloque) y **\`const\`** (ámbito de bloque, no se puede reasignar; si es un objeto, sí se pueden cambiar sus propiedades).

  - **Reglas de nombres**: empiezan por letra, \_ o $; después letras, dígitos, \_ o $; distinguen mayúsculas; **no pueden ser palabras reservadas**: var, let, const, if, else, for, while, do, switch, case, function, return, class, new, this, typeof, null, true, false, try, catch… Son válidos audio1, init, myAge; no lo son var ni 1audio.

### Tipos de datos y typeof

  - Primitivos: string, number, bigint, boolean, undefined, symbol y null. Todo lo demás es **objeto** (arrays, funciones, fechas…).

| **Expresión**           | **Resultado**                                                                  |
| ----------------------- | ------------------------------------------------------------------------------ |
| typeof "hola"           | "string"                                                                       |
| typeof 3 / typeof NaN   | "number" / "number"                                                            |
| typeof undefined        | "undefined"                                                                    |
| **\`typeof null\`**     | **"object"** (error histórico del lenguaje que se mantiene por compatibilidad) |
| typeof \[\] / typeof {} | "object" (para arrays usar Array.isArray())                                    |
| typeof function(){}     | "function"                                                                     |
| typeof new Number(3)    | "object" (objeto envoltorio, no primitivo)                                     |

### Comparación e igualdad: == frente a === 

  - **\`==\` (igualdad débil)**: compara el valor **tras convertir los tipos** (coerción). **\`===\` (igualdad estricta)**: compara **valor y tipo, sin conversión**. Los objetos se comparan **por referencia**.

  - Valores **falsy**: false, 0, -0, 0n, "", null, undefined, NaN. Todo lo demás es truthy (incluidos \[\] y {}).

let a = 3; let b = new Number(3); let c = 3;

a == b // true -\> el objeto se convierte a primitivo 3

a === b // false -\> number frente a object

b === c // false -\> object frente a number

// resultado: true false false

\[\] == \!\[\] // true

// 1) \!\[\] -\> false (un array es truthy)

// 2) \[\] == false -\> ambos a número: \[\] -\> "" -\> 0 ; false -\> 0

// 3) 0 == 0 -\> true

null == undefined // true null === undefined // false

"5" == 5 // true "5" === 5 // false

### Objetos y acceso a propiedades

  - Notación de punto obj.prop y de corchetes obj\["prop"\] u obj\[variable\] (el valor de la variable se usa como nombre). Leer una propiedad inexistente devuelve undefined; intentar leer una propiedad **de** undefined lanza TypeError.

const paciente1 = { edad: 3, andaluz: true };

const paciente2 = { nombre: "andaluz", ppm: \[34,54,45,47,41\] };

paciente1\[paciente2.nombre\] // paciente1\["andaluz"\] -\> true

paciente2.ppm\[paciente1\["edad"\]\] // ppm\[3\] -\> 47

paciente1.edad // 3

paciente2.paciente1.edad // NO válida: paciente2.paciente1 es undefined -\> TypeError

### Funciones flecha y this

  - En una función normal, this depende de cómo se llama (en obj.metodo() es obj). Las **funciones flecha (arrow functions) no tienen \`this\` propio**: lo toman del ámbito léxico que las rodea. Por eso no deben usarse como métodos de objeto:

const obj = { value: 42, getValue: () =\> this.value };

obj.getValue(); // undefined: this no es obj sino el ámbito exterior

const obj2 = { value: 42, getValue() { return this.value; } };

obj2.getValue(); // 42

## 9.3 Programación síncrona y asíncrona. Event loop

  - **Síncrono**: las operaciones se ejecutan de forma secuencial y cada una **bloquea** la ejecución hasta terminar.

  - **Asíncrono**: la operación se lanza y el programa **continúa sin bloquearse**; el resultado se procesa más tarde (callback, promesa). En web es fundamental porque las peticiones de red, temporizadores y E/S son lentos: el asincronismo mantiene la interfaz fluida y mejora la eficiencia (base de AJAX y de Node.js).

  - Mecanismos: **callbacks**, **Promises** (then, catch, finally) y **async/await** (azúcar sintáctico sobre promesas).

  - JavaScript es **monohilo** y usa el **event loop**: 1) ejecuta todo el código síncrono de la pila; 2) vacía la cola de **microtareas** (callbacks de promesas .then, queueMicrotask, await); 3) ejecuta **una macrotarea** (callbacks de setTimeout, setInterval, eventos, E/S) y vuelve al paso 2.

console.log("A");

setTimeout(() =\> console.log("B"), 0); // macrotarea

Promise.resolve().then(() =\> console.log("C")); // microtarea

console.log("D");

// salida: A D C B

  - **Closures con var y setTimeout**: la función guarda una referencia a la variable, no su valor. Con var solo existe una i compartida que al ejecutarse los callbacks vale 3; con let se crea una i por iteración.

for (var i = 0; i \< 3; i++) { setTimeout(() =\> console.log(i), 0); } // 3 3 3

for (let i = 0; i \< 3; i++) { setTimeout(() =\> console.log(i), 0); } // 0 1 2

## 9.4 Expresiones regulares

  - Sintaxis literal /patrón/flags. Métodos: regex.test(cad), cad.match(regex), cad.replace(regex, x). También en HTML5 con el atributo pattern de \<input\>.

| **Elemento**  | **Significado**                                    |
| ------------- | -------------------------------------------------- |
| AN            | Literal: los caracteres A y N seguidos             |
| \[AN\]        | Clase: UN solo carácter, A o N                     |
| \[0-9\] / \\d | Un dígito del 0 al 9                               |
| \[0-1\]       | Un dígito 0 o 1                                    |
| \\w / \\s / . | Carácter de palabra / espacio / cualquier carácter |
| {n} / {n,m}   | Exactamente n repeticiones / entre n y m           |
| \+ / \* / ?   | 1 o más / 0 o más / 0 o 1                          |
| ^ y $         | Inicio y fin de cadena (anclas)                    |
| ( ) y |       | Grupo y alternativa                                |
| Flags g, i, m | Global, sin distinguir mayúsculas, multilínea      |

**NUHSA** (Número Único de Historia de Salud de Andalucía, asignado por la BDU): letras **AN** seguidas de **10 dígitos** (p. ej. AN0123456789). La expresión /AN\[0-9\]\\d{9}/ comprueba "AN" + 1 dígito + 9 dígitos = 10 dígitos, la más completa de las opciones; /AN\[0-1\]\\d{10}/ exige 11 dígitos, /AN\\d+/ admite cualquier número de dígitos y /\[AN\]\[0-1\]\\d{9}/ solo exige una letra (A o N). Lo ideal sería anclarla: /^AN\\d{10}$/.

## 9.5 XMLHttpRequest (XHR)

  - Interfaz para hacer peticiones HTTP/HTTPS al servidor de forma asíncrona, sin recargar la página. Admite XML, JSON, HTML y texto plano.

## 9.6 AJAX (Asynchronous JavaScript and XML)

  - Técnica para desarrollar aplicaciones web interactivas (**RIA**, Rich Internet Applications): JavaScript se ejecuta en el cliente y mantiene comunicación asíncrona con el servidor en segundo plano.

  - Ventajas: interactividad, usabilidad y velocidad, porque actualiza partes de la página sin recargarla completa.

  - Componentes: HTML + CSS + DOM; objeto **XMLHttpRequest**; XML como formato de datos (hoy sobre todo JSON); y JavaScript para coordinarlo todo.

  - **Fetch API** y **Axios** simplifican las peticiones asíncronas frente al AJAX tradicional (basadas en promesas).

  - **jQuery**: biblioteca JavaScript que simplifica el recorrido y la manipulación del DOM, los eventos y AJAX.

# 10\. Web semántica

  - Extensión de la web tradicional para que las **máquinas puedan entender e interpretar** el contenido, interconectarlo y responder automáticamente a preguntas, usando lenguajes comprensibles por las máquinas.

  - Está vinculada a la **inteligencia artificial**: las máquinas pueden realizar tareas inteligentes y tomar decisiones basadas en los datos.

### Evolución de la web y cómo reconocer la web semántica en un test

  - **Web 1.0**: estática, de solo lectura. **Web 2.0**: social y **colaborativa**, basada en la participación del usuario (redes sociales, blogs, wikis). **Web 3.0 / web semántica**: web "inteligente" que comprende el significado de los datos y, gracias a ello, **se adapta al perfil y a las preferencias que va construyendo el usuario** (resultados y servicios personalizados). Algunos autores hablan de Web 4.0 (web ubicua/IoT).

  - En test: "basada en redes sociales" o "colaborativa y dialogante" = Web 2.0; "diseño que adopta nuevas tecnologías" es genérico; "se adapta a las preferencias que va perfilando el usuario" es la opción que identifica la web semántica.

## 10.1 Metadatos

  - Datos que describen otros datos; mejoran la interpretación, recuperación, organización y archivo de recursos. Esquemas: **Dublin Core** y **TEI**.

  - En HTML se incluyen con \<meta\>; en la web semántica se usan XML (codificación), RDF (datos vinculados) y OWL (ontologías del dominio).

  - Atributos de \<meta\>: name (tipo de metadato, pares nombre/valor), content (valor), charset (juego de caracteres, p. ej. UTF-8), http-equiv (equivalente a una cabecera HTTP, p. ej. content-type).

  - Nombres comunes: application-name, author, description (unos 150 caracteres), generator, keywords. Extensiones como dc.description pertenecen a **DCMI** (Dublin Core Metadata Initiative), basado en RDF.

## 10.2 Capas de la web semántica (Semantic Web Stack o "layer cake")

Jerarquía en la que cada capa aprovecha las inferiores:

  - **URI/IRI y Unicode** (capa inferior). La URI identifica recursos; en 2005 se amplió a **IRI**, que admite caracteres Unicode (chino, japonés, coreano, cirílico) y no solo ASCII; una IRI puede convertirse en URI. Unicode permite representar texto en cualquier idioma.

  - **XML** y **XML Namespaces** (espacios de nombres).

  - **RDF**: declaraciones sobre recursos en forma de **tripletas** sujeto-predicado-objeto; formato estándar de intercambio de datos semánticos. **RDFS** (RDF Schema): vocabulario básico de clases y propiedades.

  - **OWL** (Web Ontology Language): amplía RDFS con capacidades de descripción y razonamiento lógico (ontologías).

  - **SPARQL**: lenguaje de consulta sobre datos RDF/OWL.

  - **RIF** (Rule Interchange Format), **SWRL** y **RuleML**: expresión e intercambio de reglas lógicas.

  - **Seguridad** (cifrado y firma digital: confianza en las fuentes) e **interfaz de usuario** (capa superior).

### Recursos semánticos del dominio biomédico

  - **BioPortal**: repositorio abierto de **ontologías biomédicas** (más de mil: SNOMED CT, ICD, Gene Ontology…) con buscador, anotador y APIs. Lo mantiene el NCBO (National Center for Biomedical Ontology, Stanford); el enunciado del examen lo atribuye a la National Library of Medicine y lo da como respuesta correcta.

  - Otros recursos de conocimiento biomédico: **UMLS** (metatesauro de la NLM), **MeSH** (tesauro de la NLM con el que se indexa PubMed), **SNOMED CT** (terminología clínica), **Gene Ontology**, LOINC, CIE-10.

  - No son recursos de representación semántica del conocimiento en sentido estricto: **PubMed** (base de datos bibliográfica) y el **RIM de HL7** (modelo de información de referencia para mensajería e interoperabilidad).

## 11\. Normativa TIC del SAS aplicable al desarrollo web

La Dirección General de Sistemas de Información del SAS publica en su Confluence (espacios **Normativa TIC** y **Gobierno tecnológico**) normas de obligado cumplimiento para proveedores y desarrollos propios. Si el Pliego de Prescripciones Técnicas (PPT) fija otra cosa, prevalece el PPT.

### Microfrontends

  - La arquitectura de microfrontend del SAS se basa en **4 elementos**:
    
      - **HOST**: aplicación contenedora que hospeda y requiere la funcionalidad de otro contexto.
    
      - **MICROFRONTEND**: encapsula una lógica de negocio concreta de su dominio, diseñada para incorporarse a un host.
    
      - **FRAGMENT**: componente del microfrontend que representa una parte concreta de la aplicación, con funcionalidad propia y capaz de operar de forma independiente.
    
      - **CAPABILITY**: funcionalidad o contrato que un fragmento ofrece a otras partes; permite la interoperabilidad.

  - Integración host-microfront **directa** (el DOM del microfront se incorpora al del host) o **aislada** (en un contenedor independiente mediante una Isolated Capability, para hosts que no cumplen las pautas).

  - Tecnología: **TypeScript**, estándar **Web Components** y librería **Lit** (hosts nuevos y MFE exclusivamente en Lit). Comunicación: **propiedades hacia abajo, eventos hacia arriba**; la comunicación entre dos MFE la orquesta el host; no hay estado compartido.

  - Dependencias cargadas desde el **CDN del SAS** mediante **importmap**; versionado **SemVer** (Mayor.Minor.Patch); seguridad con **JWT** a partir del OpenID que proporciona el host; el host instancia el theming (el MFE no).

### Informes y plantillas

  - Objetivo: que los informes que generan las aplicaciones departamentales se vean bien en cualquier visor, sin conflictos ni problemas de seguridad.

  - Formato general: **informe en XML estructurado + plantilla XSLT**. Los informes en HTML solo se admiten excepcionalmente y con causa justificada (por tanto HTML no es el formato recomendado).

  - Contenido del informe y de la plantilla codificados en **UTF-8** (no UTF-16) y con los caracteres especiales **escapados como entidades** (\&lt;, \&oacute;, &\#243;…).

  - En las plantillas se usan **solo comillas dobles**, **no comillas simples**, porque se almacenan en base de datos y la comilla simple es carácter especial en SQL.

  - **No se recomienda usar JavaScript** en el HTML resultante (si fuera imprescindible, se siguen las "Recomendaciones JavaScript para Informes" del SAS).

  - No se referencian archivos externos (CSS, JS) salvo **imágenes estáticas**, facilitadas con la plantilla y con rutas relativas.

  - Regla general de codificación para servicios e intercambio de datos del SAS: **UTF-8**.
