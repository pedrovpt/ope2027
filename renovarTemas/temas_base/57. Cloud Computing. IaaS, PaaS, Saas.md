# CLOUD COMPUTING (COMPUTACIÓN EN LA NUBE)

  - Es un modelo de entrega de servicios que permite el acceso remoto a recursos informáticos como almacenamiento ilimitado, servidores, redes, bases de datos, SW y aplicaciones a través de internet. Este modelo elimina la necesidad de disponer de infraestructura física propia, ofreciendo en su lugar flexibilidad y escalabilidad.

  - Los usuarios pueden almacenar información, ejecutar aplicaciones y utilizar recursos informáticos, adaptados según la demanda. La gestión y entrega de estos servicios se realiza a través de servidores remotos, y los datos y programas están disponibles sin necesidad de hardware local.

  - **Características principales de la Nube:**
    
      - **Autoservicio bajo demanda:** los usuarios pueden gestionar de manera autónoma los recursos que necesitan, sin depender del proveedor.
    
      - **Pago por uso:** los usuarios pagan únicamente por los recursos que consumen, lo que optimiza los costes.
    
      - **Conexión a Internet:** acceso a los servicios desde cualquier lugar con conexión a la red.
    
      - **Versatilidad:** acceso desde muchos dispositivos (ordenadores, smartphones, tablets).
    
      - **Flexibilidad y escalabilidad:** los recursos se ajustan fácilmente según necesidades, en tiempo real.
    
      - **Trabajo multiusuario:** varias personas pueden trabajar simultáneamente en la misma aplicación o recursos sin afectar al rendimiento.
    
      - **Seguridad:** los proveedores implementan medidas avanzadas (encriptación, protección de accesos, copias de seguridad).

  - **Ventajas del Cloud Computing:**
    
      - **Escalabilidad:** los recursos se ajustan aumentando o disminuyendo la capacidad de manera eficiente.
    
      - **Ahorro económico:** muchos servicios son gratuitos y en el resto solo se paga por lo que se consume.
    
      - **Facilidad de acceso:** desde cualquier lugar y dispositivo con acceso a la red.
    
      - **Almacenamiento ilimitado:** capacidad prácticamente ilimitada, ampliable o reducible según la demanda.
    
      - **Trabajo colaborativo:** múltiples usuarios trabajan simultáneamente sobre el mismo archivo o aplicación, en tiempo real.
    
      - **Respuesta ante fallos eventuales:** tecnología avanzada de copias de seguridad que garantiza la disponibilidad de la información ante fallos de HW u otros.
    
      - **Actualización continua:** acceso automático a las últimas versiones del SW sin intervención del usuario.

  - **Desventajas del Cloud Computing:**
    
      - **Falta de información:** el usuario debe asegurarse de que el proveedor informa claramente de la ubicación de los datos, copias de seguridad y medidas de seguridad.
    
      - **Falta de soporte técnico:** se depende de que el proveedor ofrezca soporte adecuado.
    
      - **Publicidad y costes:** los servicios gratuitos pueden incluir publicidad o costes ocultos.
    
      - **Falta de conexión a Internet:** si se interrumpe, se pierde el acceso a datos y aplicaciones.
    
      - **Ataques al sistema:** exposición a ciberataques contra el proveedor.
    
      - **Protección de datos:** si el proveedor no tiene buenos protocolos puede haber pérdida de datos o incumplimiento de la normativa de protección de datos.
    
      - **Costes a largo plazo:** el pago por uso puede acumularse con el tiempo.
    
      - **Control limitado:** menor control sobre infraestructura y datos que en una solución local (on-premise).

**— Ejemplos de aplicaciones cloud y software local. ASP y el caso EDI del SAS**

**Software local (on-premise / de escritorio)** es el que se instala y ejecuta en el propio equipo del usuario. **Software en la nube (SaaS)** es el que se usa a través del navegador o de una app conectada, con los datos y el procesamiento en los servidores del proveedor.

  - **Google Docs** (Google Workspace): ofimática en la nube, edición colaborativa en tiempo real desde el navegador → SaaS.

  - **Dropbox**, Google Drive, OneDrive, iCloud: almacenamiento y sincronización de archivos en la nube → SaaS (a veces llamado STaaS, Storage as a Service).

  - **Slideshare**: plataforma web para publicar y compartir presentaciones → servicio en la nube.

  - **PowerPoint** (en su versión clásica de escritorio, instalada localmente) → **NO es cloud**: es software tradicional. En los test es la respuesta típica de “aplicación que no pertenece al Cloud Computing”. (Microsoft 365 ofrece una versión web de PowerPoint, pero en estas preguntas se entiende la aplicación de escritorio.)

  - Otros ejemplos SaaS: Gmail, Microsoft 365, Salesforce (CRM), Zoom, Slack, Canva.

**ASP (Application Service Provider / Proveedor de Servicios de Aplicación):** modelo precursor del SaaS (años 90). Un proveedor aloja y gestiona aplicaciones en sus servidores y los clientes acceden a ellas por red pagando una cuota, sin instalarlas. La diferencia con el SaaS moderno es que el ASP solía alojar una instancia por cliente (single-tenant), mientras que el SaaS usa arquitecturas multi-inquilino (multi-tenant) y web nativas. Por eso muchos proveedores describen su oferta como **“ASP-SaaS”** (aplicación en modo servicio).

**Caso del Servicio Andaluz de Salud – EDI:** el SAS utiliza el estándar **EDI (Electronic Data Interchange, Intercambio Electrónico de Datos)** para las transacciones comerciales con sus proveedores (pedidos ORDERS, avisos de expedición DESADV, confirmaciones de recepción RECADV, facturas INVOIC), alineado con las directrices de AECOC y GS1 e integrado con **SIGLO** (Sistema Integral de Gestión Logística). La Resolución de 28 de agosto de 2012 de la Dirección Gerencia del SAS estableció que la implantación se realizaría sobre la plataforma de la empresa **EDICOM**, que presta el servicio de intercambio XML/EDI **en modo ASP-SaaS** (el SAS no instala software: usa la plataforma del proveedor como servicio). Respuesta de test: **“ASP – SaaS”**.

  - No confundir con **HaaS (Hardware as a Service)**: alquiler de hardware gestionado por el proveedor; no es el caso de una solución de intercambio de documentos.

# MODELOS DE SERVICIO (IaaS, PaaS, SaaS)

## Infraestructura como Servicio (IaaS)

Proporciona acceso a recursos informáticos (servidores, almacenamiento, redes) en la nube bajo un modelo de pago por uso. Los usuarios gestionan sus propias plataformas y aplicaciones utilizando la infraestructura proporcionada por el proveedor.

  - **Funciones principales:** pago solo por lo consumido; infraestructura escalable según necesidades de procesamiento y almacenamiento; ahorro al no adquirir ni mantener hardware; alta disponibilidad (sin un único punto de fallo); facilita la virtualización de tareas administrativas.

  - **Casos de uso:** empresas sin centros de datos propios que necesitan infraestructura flexible y económica.

  - **Seguridad y cumplimiento:** el usuario tiene control total sobre la seguridad de sus aplicaciones y es responsable de las configuraciones de seguridad dentro de la infraestructura. El proveedor ofrece firewalls, VPN y otras medidas a nivel de infraestructura, pero el usuario debe cumplir la normativa de protección de datos (RGPD, HIPAA…).

  - Ejemplos: AWS EC2, Azure Virtual Machines, Google Compute Engine.

## Plataforma como Servicio (PaaS)

Ofrece un entorno completo para desarrollar, gestionar y distribuir aplicaciones. El proveedor gestiona la infraestructura subyacente (servidores, SO, middleware, entorno de ejecución o runtime), permitiendo a los usuarios centrarse en el desarrollo de sus aplicaciones.

  - **Funciones principales:** herramientas para crear, probar y alojar aplicaciones en un entorno único; el proveedor gestiona la seguridad, los sistemas operativos y las copias de seguridad; facilita la colaboración y el trabajo remoto.

  - **Casos de uso:** empresas de desarrollo con metodologías ágiles; integración eficiente de APIs.

  - **Seguridad y cumplimiento:** el proveedor gestiona infraestructura y copias, pero el usuario sigue siendo responsable de asegurar sus aplicaciones. Suelen cumplir ISO 27001 y ofrecer herramientas para cumplir el RGPD.

  - Ejemplos: Google App Engine, Heroku, Azure App Service, AWS Elastic Beanstalk, Red Hat OpenShift.

## Software como Servicio (SaaS)

Permite acceder a software y aplicaciones a través de internet mediante suscripción. Los usuarios no necesitan instalar ni actualizar el software, ya que todo se gestiona desde la nube.

  - **Funciones principales:** acceso por suscripción sin gestionar instalación ni actualización; datos almacenados y protegidos en la nube; capacidad adaptable; accesible desde casi cualquier dispositivo conectado.

  - **Casos de uso:** correo electrónico, ERP, colaboración y ofimática sin mantener infraestructura.

  - **Seguridad y cumplimiento:** el proveedor gestiona toda la seguridad a nivel de software y datos (parches, actualizaciones, cifrado en tránsito y en reposo). El cumplimiento normativo (RGPD, CCPA) es una **responsabilidad compartida** entre proveedor y usuario.

**— FaaS (Function as a Service) / Serverless y otros modelos “XaaS”**

**FaaS (Funciones como Servicio)** es el modelo **serverless** (sin servidor): el desarrollador sube funciones individuales que se ejecutan **solo cuando se produce un evento** (petición HTTP, subida de un fichero, mensaje en una cola…). El proveedor aprovisiona, escala (incluso a cero) y factura **por ejecución** (nº de invocaciones y tiempo de ejecución).

  - Ejemplos: AWS Lambda, Azure Functions, Google Cloud Functions / Cloud Run functions.

  - Características: funciones sin estado (stateless), de corta duración, dirigidas por eventos; posible latencia de arranque en frío (cold start); riesgo de dependencia del proveedor (vendor lock-in).

**Diferencia PaaS vs FaaS:** en **PaaS** se despliega una **aplicación completa** que permanece en ejecución sobre el entorno de ejecución (runtime) proporcionado por el proveedor; el desarrollador solo se ocupa del código y los datos, sin gestionar infraestructura. En **FaaS** la unidad es la **función** y solo consume recursos mientras se ejecuta. FaaS se considera una evolución/subcategoría de PaaS.

**Nota para el test (pregunta 3811):** la respuesta oficial es **PaaS**, porque la definición clásica de PaaS es “el proveedor da el entorno de ejecución y el desarrollador solo se centra en su código”. FaaS encaja también en esa descripción, así que es una pregunta discutible: si aparece, conviene fijarse en si mencionan eventos o funciones (→ FaaS) o simplemente entorno de ejecución/plataforma (→ PaaS).

**Otros modelos “XaaS” (Everything as a Service):**

  - **CaaS** (Containers as a Service): gestión de contenedores y orquestadores como servicio (Amazon ECS/EKS, Azure AKS, Google GKE).

  - **DaaS** (Desktop as a Service): escritorios virtuales en la nube (Amazon WorkSpaces, Azure Virtual Desktop). También se usa DaaS para Data as a Service.

  - **HaaS** (Hardware as a Service): alquiler de hardware gestionado por el proveedor.

  - **BaaS** (Backend as a Service): backend listo para apps (autenticación, base de datos, notificaciones), p. ej. Firebase.

  - **STaaS** (Storage as a Service), **DBaaS** (Database as a Service), **SECaaS** (Security as a Service).

## Consideraciones al elegir un modelo

No existe un modelo único válido para todas las empresas; la elección depende de las necesidades, el tipo de trabajo y los costes:

  - **IaaS:** para quien necesita gestionar su infraestructura con flexibilidad.

  - **PaaS:** para desarrolladores que necesitan un entorno de creación y pruebas sin preocuparse por la infraestructura.

  - **SaaS:** para quien quiere aplicaciones listas para usar sin gestionar el software.

| **Capa**                                        | **On-premise** | **IaaS**  | **PaaS**  | **FaaS**                 | **SaaS**    |
| ----------------------------------------------- | -------------- | --------- | --------- | ------------------------ | ----------- |
| Aplicación / funciones                          | Cliente        | Cliente   | Cliente   | Cliente (solo funciones) | Proveedor   |
| Datos                                           | Cliente        | Cliente   | Cliente   | Cliente                  | Proveedor\* |
| Runtime y middleware                            | Cliente        | Cliente   | Proveedor | Proveedor                | Proveedor   |
| Sistema operativo                               | Cliente        | Cliente   | Proveedor | Proveedor                | Proveedor   |
| Virtualización, servidores, almacenamiento, red | Cliente        | Proveedor | Proveedor | Proveedor                | Proveedor   |

\* En SaaS el cliente sigue siendo responsable del uso y del cumplimiento normativo sobre sus datos (responsabilidad compartida).

# TIPOS DE NUBES: PÚBLICAS, PRIVADAS E HÍBRIDAS

## Nube pública

Modelo estándar en Cloud Computing. El proveedor pone a disposición de los usuarios su infraestructura (SW y HW) gratuitamente o mediante pago por uso. Aplicaciones y datos se almacenan en servidores externos accesibles a través de Internet.

  - **Ejemplos:** Amazon Web Services (AWS): almacenamiento (S3), computación (EC2), bases de datos (RDS); Microsoft Azure, IBM Cloud, Google Cloud / Google App Engine…

  - **Ventajas:** acceso desde cualquier lugar; sin inversión inicial; mantenimiento a cargo del proveedor; alta flexibilidad; combinable con otros modelos; sin contratos de permanencia.

  - **Inconvenientes:** menor control sobre la seguridad (infraestructura compartida); dependencia de Internet; inactividades causadas por el proveedor.

## Nube privada

Traslada el concepto de nube pública a un entorno privado, con infraestructuras y redes propias de la empresa (o dedicadas en exclusiva). Más cercano a la computación tradicional.

  - **Ejemplo:** Microsoft Azure Stack (servicios de Azure sobre infraestructura propia); **OpenStack** (ver ampliación).

  - **Ventajas:** mayor control sobre seguridad y privacidad; reducción de costes operacionales a largo plazo; mejor rendimiento vía intranet; diseño personalizado.

  - **Inconvenientes:** inversión inicial significativa; escalabilidad limitada y costosa; necesita personal cualificado.

## Nube híbrida

Combina nube pública y privada: la infraestructura privada se usa para las cargas críticas y la pública para servicios con menores requisitos de seguridad. Los entornos que la forman son entidades únicas e individuales que se comunican mediante APIs.

  - **Ejemplo:** IBM Cloud (soluciones de nube híbrida).

  - **Ventajas:** mayor control y flexibilidad; optimización de costes; escalabilidad y elasticidad; migración gradual.

  - **Inconvenientes:** dependencia del proveedor público; complejidad de integración; riesgos de seguridad en los datos que viajan entre nubes; dependencia de la conectividad.

**— Cloud bursting y nube comunitaria**

**Cloud bursting (desbordamiento a la nube):** técnica propia de la nube híbrida por la que una aplicación que se ejecuta normalmente en la nube privada o en el CPD propio **se expande temporalmente a la nube pública cuando hay picos de demanda** que superan la capacidad local. Cuando el pico termina, los recursos públicos se liberan y solo se paga por el tiempo usado.

  - Ventaja: no hay que dimensionar el CPD propio para el pico máximo.

  - Ejemplos: campañas de vacunación, cita previa masiva, cierre fiscal, rebajas en comercio electrónico.

  - No es una migración completa a la nube pública, ni un aislamiento de la privada, ni elimina la infraestructura local.

**Nube comunitaria (community cloud):** cuarto modelo de despliegue según el NIST (SP 800-145). Infraestructura compartida por varias organizaciones con intereses o requisitos comunes (seguridad, normativa, misión), p. ej. varias administraciones públicas o servicios de salud. Puede gestionarla una de ellas o un tercero.

**Multinube (multicloud):** uso simultáneo de varios proveedores de nube pública, normalmente para evitar la dependencia de uno solo.

**— OpenStack: sistema operativo de nube**

**OpenStack** es un **sistema operativo de nube** de código abierto que **controla grandes conjuntos de recursos de computación, almacenamiento y red dentro de un centro de datos, todos gestionados y aprovisionados mediante APIs con mecanismos de autenticación comunes**. Dispone de un panel web para administradores y usuarios. Se usa sobre todo para construir **nubes privadas e IaaS** sobre infraestructura propia.

  - Origen: proyecto iniciado en 2010 por Rackspace y la NASA; hoy lo mantiene la OpenInfra Foundation con una gran comunidad.

  - Componentes principales: **Nova** (computación/máquinas virtuales), **Swift** (almacenamiento de objetos), **Cinder** (almacenamiento de bloques), **Neutron** (redes), **Keystone** (identidad y autenticación), **Glance** (imágenes), **Horizon** (panel web), **Heat** (orquestación).

Términos que aparecen como distractores:

  - **On-premise (on premises):** software o infraestructura instalados y gestionados en las instalaciones propias de la organización, frente a la nube.

  - **DevOps:** cultura y conjunto de prácticas que integran desarrollo (Dev) y operaciones (Ops) para acelerar la entrega de software (integración y despliegue continuos, automatización).

  - **DevSecOps:** DevOps con la seguridad integrada en todas las fases del ciclo de vida.

# TENDENCIAS DEL CLOUD COMPUTING

  - **Adopción de nubes híbridas y multinube:** para evitar la dependencia de un único proveedor y mejorar la resiliencia, distribuyendo cargas entre proveedores y manteniendo infraestructura local.

  - **Integración de IA y Machine Learning:** modelos avanzados sin infraestructura propia; AWS, Azure y Google Cloud desarrollan hardware específico (p. ej. TPUs) para acelerar entrenamiento y despliegue.

  - **Expansión del Edge Computing:** procesamiento de datos cerca de su origen, reduciendo la latencia (vehículos autónomos, realidad aumentada, monitorización industrial en tiempo real).

  - **Sostenibilidad y eficiencia energética:** CPD eficientes y reducción de la huella de carbono.

  - **Seguridad y cumplimiento normativo:** modelos “Zero Trust” y estrategias avanzadas de protección.

**— Soberanía del dato: GAIA-X**

**GAIA-X** es un **proyecto europeo para construir una infraestructura de datos federada, abierta y segura**, que garantice la **soberanía digital** de Europa y reduzca la dependencia de los grandes proveedores de nube no europeos.

  - Impulsado inicialmente por Alemania y Francia (presentado en 2019-2020) y gestionado por la asociación sin ánimo de lucro Gaia-X, con sede en Bruselas.

  - **No es un proveedor de nube:** define un marco común de reglas, estándares y servicios de federación (identidad, confianza, catálogo, cumplimiento) para que distintos proveedores y usuarios compartan datos y servicios de forma interoperable y transparente.

  - Principios: soberanía y protección de datos (conforme al RGPD), transparencia, interoperabilidad, portabilidad y apertura.

  - Está ligado a los **espacios de datos europeos** (salud, movilidad, industria…) de la Estrategia Europea de Datos. España tiene un hub nacional de Gaia-X.

**— Internet de las Cosas (IoT) y su relación con la nube**

**Internet de las Cosas (IoT):** se refiere a escenarios en los que la **conectividad de red y la capacidad de cómputo se extienden a objetos, sensores y artículos de uso diario** que normalmente no se consideran ordenadores, permitiéndoles generar, intercambiar y consumir datos con mínima intervención humana. La nube (y el edge computing) son la base donde se almacenan y analizan esos datos.

**Modelos de comunicación/conectividad IoT** (definidos por el IAB en la RFC 7452 y recogidos por Internet Society):

  - **Device-to-Device (dispositivo a dispositivo):** dos o más dispositivos se comunican directamente entre sí (Bluetooth, Z-Wave, ZigBee), p. ej. una bombilla y un interruptor inteligentes.

  - **Device-to-Cloud (dispositivo a la nube):** el dispositivo se conecta directamente a un servicio en la nube (Wi-Fi, Ethernet) para intercambiar datos y recibir órdenes, p. ej. un termostato inteligente.

  - **Device-to-Gateway (dispositivo a puerta de enlace):** el dispositivo se conecta a un intermediario (gateway), como una app en el móvil o un hub doméstico, que hace de puente hacia la nube.

  - **Back-End Data-Sharing (intercambio de datos a través del back-end):** permite que los datos recogidos en un servicio en la nube se exporten y combinen con datos de otras fuentes/terceros para su análisis.

**Privacidad y seguridad:** es fundamental abordarlas porque los dispositivos IoT recogen datos muy personales (hábitos, ubicación, salud) y su tratamiento tiene implicaciones sobre derechos básicos. Otros retos: interoperabilidad y estándares, dispositivos con poca capacidad para actualizaciones de seguridad, aspectos legales y regulatorios.

# HIPERCONVERGENCIA Y VIRTUALIZACIÓN DE SERVIDORES: DATOS Y APLICACIONES

## Virtualización de servidores

Proceso mediante el cual un servidor físico se divide en múltiples servidores virtuales, aislados por software. Cada servidor virtual puede ejecutar su propio SO, lo que permite ejecutar aplicaciones de manera independiente en un mismo HW. Optimiza el uso de CPU y memoria y facilita la distribución de cargas de trabajo.

### Tipos de virtualización de servidores

  - **Virtualización completa:** utiliza un hipervisor (SW que gestiona el acceso a los recursos del servidor físico y asigna recursos a cada servidor virtual).
    
      - **Hipervisor tipo 1 (nativo, bare metal o unhosted):** se ejecuta directamente sobre el hardware, sin SO anfitrión; gestiona directamente los recursos para los SO invitados. Ejemplos: VMware ESXi (vSphere Hypervisor), Xen / Citrix Hypervisor, Microsoft Hyper-V, KVM (convierte el kernel de Linux en hipervisor; las MV funcionan como procesos Linux), Proxmox VE (open source, integra KVM), **Nutanix AHV**.
    
      - **Hipervisor tipo 2 (alojado o hosted):** se ejecuta sobre un SO anfitrión; emula HW para las operaciones privilegiadas y depende del SO anfitrión. Ejemplos: Oracle VM VirtualBox, VMware Workstation, QEMU, Windows Virtual PC.
    
      - Ventaja: cada MV es completamente independiente y aislada. Inconveniente: el hipervisor consume recursos adicionales.

  - **Paravirtualización:** los SO invitados están modificados para cooperar con el hipervisor, reduciendo la sobrecarga. Mejor rendimiento que la virtualización completa, pero requiere modificar el SO invitado. Ejemplos: Xen, Virtuozzo, OpenVZ.

  - **Virtualización a nivel de sistema operativo:** sin hipervisor; el SO del servidor físico crea entornos virtuales aislados (contenedores). Menor sobrecarga, pero todos comparten el mismo SO. Ejemplos: Docker, LXC, Virtuozzo.

### Ventajas generales de la virtualización de servidores

  - Mayor disponibilidad (recursos redistribuibles entre servidores virtuales).

  - Menores costes operativos al optimizar los recursos físicos.

  - Eliminación de la complejidad de los servidores y gestión más sencilla.

  - Mejora del rendimiento de las aplicaciones y distribución rápida de cargas de trabajo.

## Hiperconvergencia

Solución de infraestructura TI que combina computación, almacenamiento y redes en una única plataforma integrada, gestionada normalmente por software en un solo dispositivo o sistema, optimizando la escalabilidad y simplificando la administración.

  - **Ventajas:** simplificación de la infraestructura; escalabilidad flexible añadiendo nodos de forma modular; reducción de costes de adquisición y mantenimiento; gestión centralizada desde una sola interfaz.

  - **Aplicaciones comunes:** centros de datos, entornos de virtualización y computación en la nube.

  - **Ejemplos:** Nutanix (con su hipervisor AHV); VxRail (Dell Technologies + VMware, integrado con vSphere y vSAN); HPE SimpliVity (integra también protección de datos).

## Virtualización de almacenamiento

Agrupa varios dispositivos de almacenamiento físico en una unidad lógica gestionada de manera centralizada, sin intervención manual en cada dispositivo.

  - **Acceso a nivel de bloque (SAN – Storage Area Network):** los bloques de datos se gestionan de manera independiente, con acceso rápido.

  - **Acceso a nivel de archivo (NAS – Network Attached Storage):** gestión centralizada de archivos.

  - **Ventajas:** seguridad adicional (autorizaciones y gestión centralizada); flexibilidad y escalabilidad; optimización de recursos sin desperdicio de espacio.

## Virtualización de escritorios y aplicaciones

La infraestructura de escritorio virtual (VDI) permite almacenar y gestionar de forma centralizada en servidores los escritorios y aplicaciones de los usuarios, accesibles desde cualquier dispositivo conectado. Ejemplos: VMware Horizon, Citrix XenDesktop (Citrix Virtual Apps and Desktops). Protocolos: RDP, X Window, ICA, NX, VNC.

  - **Ventajas:** menores costes de administración; mayor seguridad (datos en servidores controlados); facilidad para desplegar aplicaciones y escritorios; acceso desde cualquier ubicación.

  - **Desventajas:** dependencia de la infraestructura y las comunicaciones; rendimiento limitado en aplicaciones gráficas o multimedia intensivas.

# IMPLANTACIÓN DE APLICACIONES Y SERVICIOS SOBRE ARQUITECTURAS BASADAS EN CONTENEDORES

  - La virtualización de contenedores permite ejecutar aplicaciones aisladas sin iniciar un SO completo: todos los contenedores comparten el núcleo (kernel) del SO anfitrión, pero cada uno se comporta como un sistema independiente. Es más eficiente que la virtualización convencional.

  - **Funcionamiento:** el contenedor se crea a partir de una **imagen** portable que incluye la aplicación y todas sus dependencias (bibliotecas, configuraciones). La imagen se ejecuta en el SO anfitrión creando un entorno aislado.

  - **Tecnologías de contenedores:**
    
      - **Docker:** la plataforma más popular para crear y gestionar contenedores portables.
    
      - Virtuozzo (Parallels) en Windows; Jails en FreeBSD; OpenVZ y LXC en Linux.
    
      - **Kubernetes:** orquestación de grandes clústeres de contenedores (despliegue, escalado y administración automatizados).
    
      - Otros: Red Hat OpenShift, Moby, Docker Compose, Docker Swarm, Podman.

  - **Ventajas:** instalación sencilla; portabilidad; arranque muy rápido (como un proceso); aislamiento de aplicaciones; ligereza; automatización y gestión centralizada (Docker Swarm, Kubernetes); escalabilidad automática.

  - **Implantación de aplicaciones y servicios:** despliegue rápido y entrega continua; optimización de recursos; colaboración Dev/Ops con entornos idénticos de desarrollo y producción. Uso típico: aplicaciones web y **microservicios** (BD, servidor web y API como contenedores independientes, actualizables y escalables por separado).

  - **Desventajas:** seguridad (más vulnerables que las MV al compartir el kernel); complejidad de gestión en entornos grandes; dependencia de una infraestructura que soporte la tecnología.

**— Limitación de los contenedores: dependencia del SO anfitrión**

Como todos los contenedores comparten el **kernel del SO anfitrión**, tienen **menor versatilidad** que las máquinas virtuales: solo pueden ejecutar aplicaciones compatibles con ese núcleo. Una MV puede tener cualquier SO invitado; un contenedor no.

  - **Un contenedor de Windows NO puede ejecutarse en un host Linux**, porque necesita el kernel de Windows. (En sentido contrario, Windows puede ejecutar contenedores Linux, pero lo hace con una pequeña máquina virtual Linux mediante WSL2 o Hyper-V, no de forma nativa.)

  - **KVM no es una solución de contenedores**: es un **hipervisor** (virtualización completa). Las soluciones de contenedores son Docker, LXC/LXD, Podman, containerd, CRI-O, OpenVZ…

Por tanto, en el test la opción correcta es **“Menor versatilidad al depender de un solo Sistema Operativo”**.

| **Aspecto**             | **Máquina virtual**                 | **Contenedor**                            |
| ----------------------- | ----------------------------------- | ----------------------------------------- |
| Qué virtualiza          | El hardware (mediante hipervisor)   | El sistema operativo (espacio de usuario) |
| SO                      | Cada MV tiene su propio SO completo | Comparten el kernel del anfitrión         |
| Tamaño / arranque       | GB / minutos                        | MB / segundos o menos                     |
| Aislamiento / seguridad | Mayor                               | Menor (kernel compartido)                 |
| Versatilidad de SO      | Cualquier SO invitado               | Solo compatible con el kernel del host    |

**— Docker: conceptos básicos y comandos principales**

**Conceptos:** **imagen** (plantilla de solo lectura con la aplicación y sus dependencias, organizada en capas); **contenedor** (instancia en ejecución de una imagen); **Dockerfile** (fichero de texto con las instrucciones para construir una imagen: FROM, RUN, COPY, CMD, EXPOSE…); **registro** (repositorio de imágenes, p. ej. Docker Hub); **volumen** (almacenamiento persistente); **Docker Engine** (demonio dockerd + cliente docker).

| **Comando**                    | **Función**                                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| docker ps                      | Lista los contenedores en ejecución (con -a, también los detenidos). Equivale a docker container ls. |
| docker start                   | Inicia un contenedor detenido (ya existente).                                                        |
| docker stop / docker restart   | Detiene / reinicia un contenedor.                                                                    |
| docker run                     | Crea un contenedor nuevo a partir de una imagen y lo arranca (pull + create + start).                |
| docker create                  | Crea un contenedor sin arrancarlo.                                                                   |
| docker build                   | Construye una imagen a partir de un Dockerfile (p. ej. docker build -t miapp:1.0 .).                 |
| docker stats                   | Muestra en tiempo real el consumo de recursos (CPU, memoria, red, E/S) de los contenedores.          |
| docker images                  | Lista las imágenes locales (equivale a docker image ls).                                             |
| docker pull / docker push      | Descarga / sube una imagen a un registro.                                                            |
| docker rm / docker rmi         | Elimina un contenedor / una imagen.                                                                  |
| docker exec                    | Ejecuta un comando dentro de un contenedor en marcha (p. ej. docker exec -it c1 bash).               |
| docker logs                    | Muestra los registros (salida) de un contenedor.                                                     |
| docker inspect                 | Muestra información detallada (JSON) de un contenedor, imagen, red o volumen.                        |
| docker info / docker version   | Información general del sistema Docker / versión de cliente y servidor.                              |
| docker save / docker load      | Exporta imágenes a un .tar / carga imágenes desde un .tar.                                           |
| docker network / docker volume | Gestión de redes y volúmenes.                                                                        |
| docker compose up / down       | Levanta / detiene una aplicación multicontenedor definida en compose.yaml.                           |

Distractores habituales que **no existen** en Docker: docker ls, docker show, docker up (sí existe docker compose up), docker init\* como “arrancar contenedor”, docker on, docker compile, docker create-image, docker forge, docker monitor. (\*docker init existe en versiones recientes, pero sirve para generar ficheros iniciales Dockerfile/compose de un proyecto, no para iniciar contenedores.)
